# Olivia 모바일 한 화면 최적화 설계

## 목표

모바일 Olivia OS의 기존 정보와 기능을 유지하면서 홈을 작은 휴대폰 한 화면에 맞추고, 캘린더 할 일·플로팅 Dock·문서 승인·대화 기록 밀도를 개선한다. 데스크톱 UI와 데이터 모델은 변경하지 않는다.

## 범위

1. 모바일 홈을 375×812 뷰포트에서 세로 스크롤 없이 사용할 수 있게 축소한다.
2. 모바일 캘린더에 데스크톱과 같은 공용 할 일 영역을 추가한다.
3. 모바일 하단 메뉴를 화면 가장자리에서 떨어진 플로팅 Dock으로 바꾼다.
4. 모바일 문서 미리보기에 오렌지 승인 버튼과 고객등록 연결 흐름을 추가한다.
5. 모바일 채팅 오른쪽 대화 기록 네비게이터를 현재보다 두 배 촘촘하게 만든다.

## 접근 방식

모바일 전용 컴포넌트와 CSS만 수정한다. 데스크톱 컴포넌트를 모바일에 직접 삽입하거나 모바일 전체 구조를 다시 만들지 않는다. 기존 API와 상태 모델을 재사용해 데이터와 동작의 중복을 피한다.

## 모바일 홈

- 홈 헤더, 인사말, 오늘 일정, 현재 작업, 빠른 메뉴 여섯 개, Olivia 명령 카드를 모두 유지한다.
- 기준 뷰포트는 375×812이며 Safe Area를 제외한 영역에서 세로 스크롤이 생기지 않게 한다.
- 세로 여백, 카드 패딩, 아이콘, 제목과 보조문구를 함께 축소한다.
- 빠른 메뉴는 2열 3행을 유지하되 한 카드의 높이를 줄인다.
- 버튼의 실제 터치 영역은 최소 44px을 유지한다.
- 더 큰 화면에서는 과도하게 작아지지 않도록 높이 기반 미디어 쿼리와 `clamp()`를 사용한다.

## 모바일 캘린더 할 일

- 기존 `/api/calendar/todos`를 사용하고 별도 모바일 데이터 모델을 만들지 않는다.
- 할 일은 날짜별 일정과 구분되는 공용 목록으로 일정 목록 아래에 배치한다.
- 목록 조회, 새 할 일 추가, 완료 상태 전환, 삭제를 지원한다.
- 추가와 수정은 낙관적 갱신 또는 즉시 반영 후 실패 시 원복하며, 오류 메시지와 재시도 경로를 제공한다.
- 일정 생성·수정 흐름과 캘린더 보기 전환은 변경하지 않는다.

## 플로팅 하단 Dock

- 메뉴 개수와 순서 `홈 · 캘린더 · 메모 · 문서 · 올리비아 채팅`을 유지한다.
- 좌우 10px 안쪽, Safe Area 위에 떠 있는 둥근 반투명 Surface로 표시한다.
- 데스크톱 Dock과 같은 깊이감을 주는 Border, Blur, Shadow를 적용한다.
- 활성 메뉴는 기존 Mint Surface와 Deep Green 텍스트를 유지한다.
- 각 화면의 하단 패딩을 Dock의 실제 높이와 간격에 맞춘다.

## 미리보기 승인과 고객등록

- 공유, 다운로드, 수정 요청과 함께 오렌지 `승인` 버튼을 표시한다.
- 승인 가능한 대상은 `temporaryDocumentId`가 있는 임시문서다. 연결되지 않은 정식 문서에서는 승인 버튼을 비활성화하고 이유를 안내한다.
- 첫 번째 승인에서 `PATCH /api/temporary-documents/:id`의 `approve_content`를 호출해 상태를 `pending_client`로 변경한다.
- 성공하면 같은 화면에 `고객으로 등록할까요?` 확인 UI를 표시한다.
- 두 번째 확인에서 같은 API의 `link_client`를 호출해 기존 고객등록·워크플로 생성·관련 문서 연결 로직을 실행한다.
- 고객등록을 취소해도 내용 승인 상태는 유지하며 문서는 삭제하지 않는다.
- 성공 후 문서를 다시 불러오고 `olivia-resource-updated` 이벤트를 발생시킨다.
- 중복 탭을 막고 서버 오류를 미리보기 알림 영역에 표시한다.

## 채팅 대화 기록 네비게이터

- 모바일 전용 Tick 높이를 22px에서 11px로 줄인다.
- Rail 폭 32px과 기본·활성 막대 너비는 유지해 터치 위치와 현재 대화 식별성을 보존한다.
- Tick 버튼의 시각적 밀도만 변경하며 팝오버, 대화 이동, 데스크톱 Navigator 동작은 유지한다.

## 상태와 오류 처리

- 캘린더 일정 오류와 할 일 오류는 독립적으로 표시한다.
- 할 일 저장 중에는 중복 요청을 막고 실패 시 사용자가 입력을 잃지 않게 한다.
- 승인과 고객등록은 각각 별도 Busy 상태를 사용한다.
- 미리보기 승인 대상이 아니면 기존 공유·다운로드·수정 요청은 그대로 동작한다.

## 검증

- 375×812에서 홈의 모든 섹션과 플로팅 Dock이 한 화면에 들어오는지 확인한다.
- 390×844와 430×932에서 여백이 지나치게 벌어지지 않는지 확인한다.
- 모바일 캘린더에서 할 일 조회·추가·완료·삭제와 오류 복구를 확인한다.
- 임시문서 미리보기에서 내용 승인 후 고객등록 확인이 이어지고, 두 번째 확인 전에는 고객이 생성되지 않는지 확인한다.
- 모바일 Navigator Tick 높이가 11px이고 데스크톱 값은 유지되는지 확인한다.
- TypeScript, ESLint, 관련 단위 테스트, 프로덕션 빌드를 실행한다.

## 제외 범위

- 데스크톱 홈·캘린더·Dock 재설계
- 모바일 메뉴 항목 추가 또는 순서 변경
- 캘린더 일정 데이터 모델 변경
- 첫 번째 승인만으로 고객을 자동 생성하는 동작
- 새로운 고객등록 API 또는 별도 모바일 데이터 저장소

# 공동·개인별 셀렉 서버 기준 동기화 설계

작성일: 2026-11-11
대상: 공동 프로젝트 셀렉, 개인별 셀렉, 관리자 진행 현황, RAW 매칭

## 1. 목표

고객 화면과 관리자 화면이 같은 서버 저장값과 같은 셀렉 계산 규칙을 사용한다. 브라우저에서 아직 저장되지 않은 변경은 서버 셀렉으로 계산하지 않으며, 임시 표시와 미저장 상태를 명확히 노출한다.

기존 공동 초안·제출, 개인별 선택·주문·제출, 관리자 Bridge, RAW 매칭 데이터는 삭제하거나 대체하지 않는다. 새 사진별 상태 저장소를 서버 기준으로 추가하고 기존 저장소를 호환용으로 함께 갱신한다.

## 2. 선택한 접근

사진별 상태 행과 배치 RPC를 사용한다.

- JSON 전체 덮어쓰기를 사진별·필드별 갱신으로 바꾼다.
- 동일한 변경을 재전송해도 결과가 달라지지 않도록 `client_id`와 `client_seq`를 기록한다.
- 별점, 컬러, 메모, 선택 여부는 각자 갱신 시각을 가진다.
- 서로 다른 사진을 고친 두 기기의 변경은 모두 남는다.
- 같은 사진·같은 필드는 더 최신인 변경만 반영한다.
- 기존 공동 초안 JSON과 `person_select_choices`는 기존 기능 호환을 위해 같은 트랜잭션에서 갱신한다.

기존 JSON 안에서만 병합하는 방식은 큰 초안을 반복 기록하고 관리자 집계가 느려지는 문제가 남아 제외한다. 공개 브라우저가 Supabase Realtime에 직접 쓰는 방식은 공개 토큰 권한 범위를 넓혀 제외한다.

## 3. 데이터 모델

새 마이그레이션은 다음 서버 전용 테이블을 추가한다.

### 3.1 사진별 상태

`person_select_selection_item_states`

- `event_id`
- `person_id` 또는 `reviewer_id` 중 정확히 하나
- `image_id`, `category_key`
- `selected`, `rating`, `color_label`, `memo`, 개인별 보정 요청용 `retouch_keys`
- 필드별 `*_updated_at`
- 필드별 마지막 `client_id`, `client_seq`
- 서버의 마지막 반영 시각 `updated_at`

유일성은 공동 셀렉에서 `(event_id, reviewer_id, image_id)`, 개인별 셀렉에서 `(event_id, person_id, image_id)`로 보장한다. 선택 해제 행도 tombstone으로 남겨 오래된 재시도가 선택을 되살리지 못하게 한다.

### 3.2 멱등 처리

`person_select_selection_diff_receipts`

- actor 범위와 `client_id`, `client_seq`를 유일 키로 둔다.
- 같은 배치를 다시 받으면 저장된 결과를 반환하고 상태를 다시 변경하지 않는다.
- 오래된 receipt는 운영 보관 기간에 맞춰 정리할 수 있도록 생성 시각 인덱스를 둔다.

### 3.3 저장 실패 기록

`person_select_selection_save_failures`

- event, person/reviewer, API 단계, 오류 코드, 발생 시각, 복구 시각을 저장한다.
- 토큰, PIN, 메모 본문, 사진 원본 경로는 기록하지 않는다.
- 브라우저 네트워크 단절은 다음 재시도 요청의 복구 정보로 서버에 기록한다.

세 테이블은 RLS를 켜고 `anon`, `authenticated` 접근을 회수한다. 서비스 역할만 접근하며 공개 API가 토큰·세션을 다시 검증한다.

## 4. 서버 저장 흐름

### 4.1 공동 셀렉

`PUT /api/pick/shared/[shareToken]/draft`가 기존 전체 초안과 새 diff 요청을 모두 받는다.

1. 공유 토큰과 활성 검토자를 검증한다.
2. 검토자+공유 토큰 기준 분당 60회 제한을 적용한다.
3. 요청한 image ID만 프로젝트 소속인지 확인한다.
4. 최대 200개 diff를 RPC에 전달한다.
5. RPC가 사진별·필드별 최신 시각과 client sequence를 비교해 반영한다.
6. 기존 `person_select_shared_drafts.items`와 revision을 호환 갱신한다.
7. 서버가 확정한 전체 스냅샷, 반영된 diff, 무시된 오래된 diff, 마지막 저장 시각을 반환한다.

기존 전체 초안 요청은 계속 지원해 구버전 고객 링크가 깨지지 않게 한다.

### 4.2 개인별 셀렉

새 배치 경로 `PUT /api/pick/[eventSlug]/choices/batch`를 추가한다.

1. 기존 쿠키 세션으로 사람과 프로젝트를 검증한다.
2. 사람+프로젝트 기준 분당 60회 제한을 적용한다.
3. 이미지 소유자, 항목, 선택 가능 수량, 메모 길이를 검증한다.
4. 사진별 상태를 최신값 우선으로 반영한다.
5. 선택 상태를 기존 `person_select_choices`에 같은 트랜잭션으로 materialize한다.
6. 기존 주문 정리, 히스토리, last seen 동작을 유지한다.

기존 단건 PUT/DELETE는 구버전 화면 호환을 위해 남긴다.

### 4.3 rate limit

- IP는 저장 제한 키에서 제외한다.
- 공동은 reviewer ID와 share token hash, 개인별은 person ID와 event ID를 사용한다.
- 한도 초과는 큐를 버리게 하는 일반 실패가 아니라 `retryAfter`가 있는 자동 저장 대기 응답으로 돌려준다.
- 읽기·제출·다운로드 제한은 현재 정책을 유지한다.

## 5. 고객 저장 큐

공통 클라이언트 모듈은 다음을 담당한다.

- 사진별 변경을 마지막 값으로 합쳐 2초 동안 모은다.
- 요청당 최대 200건을 보낸다.
- 실패하면 1초, 2초, 5초, 10초 이후 재시도하고 이후에도 10초 간격으로 유지한다.
- 큐와 client sequence를 버전이 붙은 localStorage 키에 백업한다.
- 같은 actor와 프로젝트에서만 백업을 복구한다.
- 저장 중 새 변경이 생기면 다음 배치로 남긴다.
- 창 focus와 `visibilitychange` 복귀 때 서버 스냅샷을 읽고, 서버값 위에 아직 전송하지 않은 임시 변경만 다시 얹는다.

화면의 정식 별점·컬러·셀렉 수는 서버 확인값으로 계산한다. 미저장 변경은 흐린 임시 표시와 작은 빨간 점으로 보이며 셀렉 수에는 포함하지 않는다.

## 6. 저장 상태 UI

기존 고객 화면의 하단 상태 영역을 재사용한다.

- `저장됨 · 방금`
- `저장 중…`
- `저장 안 된 변경 N건 · 다시 시도`
- rate limit 대기 중에는 `잠시 후 자동 저장 · N건`

미저장 사진에는 작은 점만 추가한다. 새 색 체계나 별도 카드 UI를 만들지 않는다. 미저장 또는 전송 중 diff가 있으면 `beforeunload` 경고를 등록하고 최종 제출을 비활성화한다. 제출 API는 서버에 미저장 diff가 없는지도 다시 검증한다.

## 7. 공통 셀렉 계산

`countCustomerSelection`과 `isCustomerSelection`을 순수 함수로 둔다.

- 별점 1~5 또는 컬러 6~9가 있으면 Bridge 셀렉이다.
- 개인별 classic 선택은 서버의 `selected=true`를 같은 함수 입력 형식으로 변환한다.
- 고객 화면, 관리자 집계, 공동 RAW 매칭 대상 계산이 같은 함수를 사용한다.
- 관리자 숫자에는 `서버 기준 · 마지막 저장 상대시각 · 검토자/사람 이름`을 함께 표시한다.

## 8. 관리자 동기화 확인

기존 관리자 툴바에 보조 버튼 `동기화 확인`을 추가한다.

- 공동: 검토자별 서버 저장 장수, 마지막 저장 시각, pending 실패 건수
- 개인별: 사람별 서버 저장 장수, 마지막 저장 시각, pending 실패 건수
- 전체 최근 저장 실패 수가 있으면 기존 경고 톤으로 한 줄 표시한다.

관리자 데이터는 화면이 보일 때만 30초마다 갱신하고, 창 focus 시 즉시 갱신한다. 동일 요청이 겹치지 않게 진행 중 요청을 재사용한다.

## 9. 제출과 RAW 매칭

- 최종 제출은 서버 스냅샷에서 항목을 만들며 브라우저의 임시 상태를 제출하지 않는다.
- 제출 전에 미저장 큐가 있으면 실행을 막는다.
- 기존 제출 기록과 request key 멱등 처리는 유지한다.
- 공동 RAW 매칭은 호환 갱신된 공동 초안 또는 동일 서버 상태 조회 결과만 사용한다.
- 개인별 RAW 매칭은 materialize된 `person_select_choices`만 사용한다.

## 10. 오류 처리

- 네트워크 오류와 5xx는 큐 유지 후 자동 재시도한다.
- 인증 만료·권한 오류는 자동 재시도를 중단하고 다시 로그인 안내를 표시한다.
- 잘못된 image ID·메모 길이·항목 수량 오류는 해당 diff를 실패 상태로 남기고 사용자에게 이유를 표시한다.
- 서버는 저장 실패를 구조화해 기록하되 민감정보를 로그에 남기지 않는다.
- 구버전 revision 충돌 응답은 기존 PT409 처리를 유지한다.

## 11. 테스트

### 단위 테스트

- 별점·컬러·classic 선택의 공통 셀렉 수 계산
- diff 병합과 마지막 값 압축
- 동일 client sequence 멱등 처리
- 필드별 최신 시각 우선과 동률 tie-break
- localStorage 직렬화·복구
- 재시도 간격과 200건 분할

### API·DB 테스트

- 별점 100회 연타 시 5요청 이하
- 같은 배치 두 번 전송 시 같은 결과
- 서로 다른 기기의 서로 다른 사진 변경이 모두 보존
- 같은 IP의 검토자 3명 저장 성공
- 공동 초안 JSON과 사진별 상태 일치
- 개인별 상태와 `person_select_choices` 일치
- 실패 기록과 복구 시각 저장

### 화면 회귀

- 공동 classic, 고객 Bridge, 개인별 classic의 기존 선택 동작 유지
- 미저장 점·하단 상태·beforeunload·제출 잠금
- 고객 셀렉 수와 관리자 셀렉 수 일치
- 관리자 30초·focus 갱신과 동기화 확인
- 기존 제출, 리뷰, 전체화면, RAW 매칭 유지

## 12. 배포 순서

1. 마이그레이션 파일 생성 및 로컬 검증
2. 서버가 구·신 클라이언트를 동시에 지원하도록 배포
3. 운영 SQL은 별도 확인 후 적용
4. 고객 큐 UI 배포
5. 관리자 동기화 확인 및 지표 점검

마이그레이션이 아직 적용되지 않은 환경에서는 기존 저장 경로로 동작하도록 서버 기능 감지를 둔다. 기존 데이터 삭제나 일괄 초기화는 하지 않는다.

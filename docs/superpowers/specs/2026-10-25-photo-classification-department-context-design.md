# 사진 분류 진료과 자동 연결 설계

작성일: 2026-10-25

## 1. 목적

사진 분류가 이미 등록된 고객·프로젝트 또는 촬영 폴더에서 진료과를 확인할 수 있는데도 사용자에게 같은 정보를 다시 묻는 문제를 해결한다.

정형외과·신경외과·마취통증의학과·재활의학과는 현재 사진 분류에서 같은 장면 규칙을 사용하므로 하나의 `근골격·통증계` 분류 그룹으로 자동 연결한다. 고객 데이터에는 원래 진료과 명칭을 그대로 보존하고, 사진 분류 내부에서만 기존 `orthopedics_neurosurgery` 키를 공통 그룹으로 사용한다.

완료 기준은 다음과 같다.

- 신뢰할 수 있는 진료과 정보가 있으면 선택 단계를 건너뛴다.
- Bridge에서 사진 분류로 이동해도 확인된 진료과가 유지된다.
- 진료과를 알 수 없거나 서로 충돌할 때만 사용자에게 선택 또는 확인을 요청한다.
- 기존 고객 데이터와 사진 분류 저장값에 대한 마이그레이션이 필요하지 않다.

## 2. 확인된 문제

현재 구현에는 공통 분류 설정 `orthopedics_neurosurgery`가 있고 실제 프롬프트도 네 진료과를 모두 같은 규칙으로 처리한다. 그러나 진입 경로마다 진료과 상태가 따로 관리되어 다음 문제가 생긴다.

- `departmentFromPhotoText`는 정형외과·신경외과·통증 표현은 인식하지만 재활의학과는 인식하지 못한다.
- 사진 분류의 표시명과 선택 항목은 `정형외과/신경외과`로만 보여 실제 적용 범위를 드러내지 않는다.
- 사진작업실 창으로 전달된 `clientId`와 `workflowRunId`가 내부 사진 분류 컴포넌트까지 이어지지 않는다.
- Bridge Scene 계획은 폴더와 Scene 경계만 전달하고 진료과는 전달하지 않는다.
- 사진 분류 로컬 상태의 기본값이 `dermatology`라 진료과 전달이 끊긴 경로에서 피부과로 오인될 수 있다.
- 이전 채팅형 사진 분류 흐름은 병원 현장촬영을 고르면 폴더나 등록 고객 정보를 확인하기 전에 항상 진료과 선택 단계로 이동한다.

## 3. 검토한 접근 방식

### A. 키워드와 화면 문구만 보완

재활의학과 키워드를 추가하고 선택 항목 이름을 네 과로 확장한다. 변경량은 작지만 이미 등록된 데이터를 재사용하지 못해 선택 단계가 계속 나타난다.

### B. 공통 진료과 해석기와 컨텍스트 자동 연결 — 채택

진료과 표현을 내부 분류 그룹으로 바꾸는 순수 해석기와, 고객·프로젝트·폴더에서 후보를 수집하는 컨텍스트 해석기를 둔다. 모든 사진 분류 진입 경로가 같은 결과 계약을 사용한다. 확인된 값은 자동 적용하고, 출처를 화면에 표시하며, 알 수 없거나 충돌할 때만 선택을 요청한다.

기존 분류 키와 규칙을 유지하면서 반복 질문을 없앨 수 있고 Bridge·사진작업실·채팅·NAS 실행의 판단 차이도 줄일 수 있다.

### C. 네 진료과를 별도 내부 타입으로 분리

각 과를 별도 `MedicalDepartment`로 만들고 공통 규칙을 상속한다. 장래의 과별 세부 장면에는 유리하지만 현재 결과가 거의 같아 타입, 저장값, API, 원격 Worker 호환 범위를 불필요하게 넓힌다. 과별 차이가 실제 요구로 확인될 때 후속 설계로 검토한다.

## 4. 진료과 모델

내부 키 `orthopedics_neurosurgery`는 변경하지 않는다. DB 저장값, Worker payload, 체크포인트, 기존 테스트와의 호환을 유지하기 위해 새 키와 데이터 마이그레이션을 만들지 않는다.

사용자 표시명은 `근골격·통증계`로 통일하고 보조 설명에 `정형외과 · 신경외과 · 마취통증의학과 · 재활의학과`를 표시한다. 고객 레코드의 `specialty` 또는 `department` 원문은 수정하지 않는다.

공통 그룹으로 인식할 대표 표현은 다음과 같다.

- 정형외과, 정형
- 신경외과
- 마취통증의학과, 마취통증, 통증의학과, 통증클리닉, 통증
- 재활의학과, 재활

`신경과`처럼 다른 전문과로 해석될 수 있는 표현은 `신경외과`와 동일시하지 않는다. 부분 문자열은 긴 표현부터 판별해 성형외과를 정형외과로 잘못 읽는 것과 같은 오탐을 막는다.

## 5. 해석 결과 계약

공통 해석기는 단순한 `MedicalDepartment | null` 대신 다음 의미를 가진 결과를 반환한다.

- `resolved`: 자동 적용 가능한 단일 진료과 그룹
- `unknown`: 확인 가능한 진료과 정보가 없음
- `conflict`: 두 개 이상의 신뢰할 수 있는 출처가 서로 다른 그룹을 가리킴

해결된 결과에는 다음 정보를 포함한다.

- 내부 `MedicalDepartment`
- 사용자 표시명
- 원래 진료과 문자열
- 판별 출처
  - 사용자가 직접 변경한 값
  - 연결된 고객
  - 연결된 프로젝트
  - 폴더명과 정확히 일치한 등록 고객
  - 폴더명 키워드

이 출처 정보는 자동 적용 이유를 설명하고, Bridge 계획과 사진 분류 세션에서 같은 판단을 유지하는 데 사용한다.

## 6. 판별 순서와 충돌 규칙

자동 판별은 다음 순서로 근거를 수집한다.

1. 사진작업실 창 또는 현재 Olivia 컨텍스트에 연결된 고객·프로젝트의 진료과
2. 날짜 접두어를 제거한 폴더명과 정확히 일치하는 등록 고객의 진료과
3. 폴더명에 명확히 포함된 진료과 표현

사용자가 화면에서 `변경`을 눌러 직접 고른 값은 해당 작업 세션에서 가장 높은 우선순위의 확정값이 된다.

서로 다른 자동 출처가 같은 내부 그룹을 가리키면 충돌이 아니다. 예를 들어 고객 데이터가 `재활의학과`이고 폴더명이 `강재활의학과`이면 둘 다 `근골격·통증계`이므로 자동 적용한다.

연결된 고객은 피부과인데 폴더명은 정형외과처럼 서로 다른 그룹을 가리키면 한쪽을 조용히 선택하지 않는다. `등록 고객은 피부과, 폴더명은 근골격·통증계로 확인됩니다.`라는 한 줄 안내와 선택 항목을 보여 사용자가 확정하게 한다. 사용자가 확정하기 전에는 진료과 로직이 필요한 분석을 시작하지 않는다.

## 7. 데이터 흐름

### 사진작업실과 Bridge

1. 사진작업실 또는 Bridge가 창 컨텍스트의 `clientId`, `workflowRunId`와 현재 폴더명을 공통 해석기에 전달한다.
2. 해석기는 등록 데이터와 폴더 근거를 확인해 `resolved`, `unknown`, `conflict` 중 하나를 반환한다.
3. `resolved`이면 사진 분류 상태에 진료과를 자동 적용한다.
4. Bridge가 Scene 계획을 만들 때 진료과 해석 결과와 출처를 계획에 함께 넣는다.
5. 사진 분류가 Bridge 계획을 소비할 때 Scene 경계와 진료과를 함께 복원한다.
6. 계획의 진료과가 없거나 현재 컨텍스트와 충돌하면 Scene 분석 결과는 폐기하지 않고 진료과 확인만 먼저 받는다. 확인 후 기존 Scene 검토 단계로 이동하며 특징 추출과 경계 분석은 반복하지 않는다.

진료과 필드가 추가되므로 Bridge 계획 버전을 올린다. 계획은 현재 브라우저 메모리에만 존재하므로 DB 마이그레이션은 없으며, 지원하지 않는 이전 버전은 기존 계획 유효성 검사에서 거부한다.

### 채팅형 사진 분류

1. 병원 현장촬영을 선택해도 즉시 진료과를 묻지 않는다.
2. 연결된 고객·프로젝트로 이미 해결되면 해당 값을 적용하고 폴더 선택으로 이동한다.
3. 연결 정보가 없으면 폴더를 먼저 선택하고 스캔한 뒤 폴더명과 등록 고객을 확인한다.
4. 해결되면 진료과 선택 단계를 건너뛰고 다음 분류 설정으로 이동한다.
5. `unknown` 또는 `conflict`일 때만 진료과 선택 단계를 보여준다.

### NAS/원격 분류

기존 `폴더명 → 정확히 일치하는 등록 고객 → 알 수 없으면 중단` 흐름은 유지하되 같은 공통 표현 해석기를 사용한다. 재활의학과도 근골격·통증계로 자동 판별하며, 알 수 없는 진료과에 `general`이나 `dermatology` 기본값을 넣지 않는다.

## 8. UI와 상호작용

사진을 판단하는 기존 중성 다크 작업 패널과 2단계 탭 구조를 유지한다. 새 탭이나 새 전역 색상은 만들지 않는다.

진료과가 자동 적용된 경우 큰 선택 카드 전체를 반복 노출하지 않는다. 설정 요약에 다음 한 줄을 표시한다.

`근골격·통증계 적용됨 · 등록 고객 정보`  `변경`

- `변경`은 배경 없는 약한 동작으로 표시한다.
- 사용자가 `변경`을 누를 때만 기존 진료과 선택 항목을 펼친다.
- 원래 고객 진료과가 재활의학과라면 보조 문구에 `재활의학과 → 근골격·통증계 규칙`을 표시한다.
- 자동 적용 상태 자체를 새로운 단계나 세 번째 탭으로 만들지 않는다.

`unknown`이면 기존 선택 UI를 표시하되 `등록 고객과 폴더명에서 진료과를 찾지 못했습니다.`를 먼저 설명한다. `conflict`이면 충돌한 두 근거를 함께 표시한다. 비활성 실행 버튼 아래에는 `진료과를 확인해야 분류를 시작할 수 있습니다.`를 표시한다.

Bridge의 Scene 검토 창은 기존 단일 주 실행 버튼을 유지한다. 진료과가 해결되지 않았을 때는 같은 창 안에서 진료과 확인을 마친 뒤 버튼을 활성화한다. 확인된 경우에는 별도의 선택 단계를 보여주지 않는다.

## 9. 컴포넌트와 모듈 책임

### 진료과 표현 해석기

- 한국어 진료과 원문을 기존 `MedicalDepartment`로 정규화한다.
- 근골격·통증계 네 과와 축약 표현을 한곳에서 관리한다.
- UI, 네트워크, React 상태를 알지 않는 순수 함수로 유지한다.

### 진료과 컨텍스트 API/서비스

- `clientId`, `workflowRunId`, 폴더명을 입력으로 받는다.
- 연결된 고객·프로젝트와 정확히 일치하는 등록 고객을 조회한다.
- 해석 근거와 충돌을 결과 계약으로 반환한다.
- 조회 실패를 특정 진료과로 대체하지 않는다.

### `PhotoStudioExecutionContext`

- 현재 사진 작업 세션의 진료과 해석 결과를 폴더와 함께 보관한다.
- 폴더가 바뀌면 이전 폴더에서 유래한 자동 판별값을 폐기한다.
- 사용자가 직접 확정한 값과 자동 판별값의 출처를 구분한다.

### `OliviaBridgeWorkspace`

- 현재 폴더의 진료과 해석 상태를 표시한다.
- 해결된 진료과를 Bridge 분류 계획에 포함한다.
- 알 수 없거나 충돌한 상태에서는 계획을 잃지 않고 진료과 확인을 요청한다.

### `PhotoSortingWorkspace`

- 전달된 진료과 해석 결과로 로컬 `department` 상태를 초기화한다.
- 해결된 진료과는 요약형으로 표시하고 기존 선택 그리드를 접는다.
- 사용자 변경 뒤에는 자동 판별 effect가 값을 다시 덮어쓰지 않게 한다.
- Bridge 계획 적용 시 Scene과 진료과를 한 번에 복원한다.

### 채팅형 사진 분류 상태

- 흐름 시작 시 연결된 고객·프로젝트 컨텍스트를 확인한다.
- 폴더 선택 뒤 공통 해석 결과에 따라 `choose_department` 단계를 조건부로 사용한다.
- 기존 조명, 경계시간, 분석 방식, 옵션 수집과 handoff 구조는 보존한다.

## 10. 오류 처리와 안전 장치

- 고객 또는 프로젝트 조회 실패만으로 특정 진료과를 확정하지 않는다. 실패 이유를 기록하고 폴더 근거를 계속 확인하며, 모든 근거 확인이 끝나도 값이 없을 때만 `unknown`으로 처리한다.
- 접근 권한이 없는 폴더는 진료과 문제가 아니라 기존 폴더 접근 오류로 표시한다.
- 자동 출처가 충돌하면 사용자의 명시적 선택 전까지 분석을 시작하지 않는다.
- Bridge 계획 적용 시 현재 컨텍스트를 다시 해석한 결과가 계획에 기록된 그룹과 다르면 자동 적용하지 않고 충돌 확인 상태로 전환한다.
- 저장된 이전 세션의 진료과는 같은 폴더의 유효한 세션을 복원할 때만 사용한다.
- `unknown` 상태에서 피부과 또는 기타를 기본값처럼 선택해 두지 않는다.

## 11. 기존 기능 보존

다음 기능과 데이터는 변경하지 않는다.

- 고객 레코드의 원래 `specialty`/`department` 문자열
- 내부 `MedicalDepartment` 키와 원격 Worker payload 형식
- 근골격·통증계의 기존 Scene 규칙과 프롬프트
- Bridge Scene 경계 분석 결과와 파일 서명 검증
- Scene 합치기·나누기·이름 변경·최종 정리
- RAW 보호, JPG 준비, 셀렉, RAW 매칭, 보정, 리사이즈, 이름 변경
- 진료과와 무관한 사진 분류 옵션 및 기본값

## 12. 테스트 전략

### 단위 테스트

- 정형외과·신경외과·마취통증의학과·재활의학과와 대표 축약어가 모두 `orthopedics_neurosurgery`로 정규화되는지 확인
- 성형외과와 신경과를 근골격·통증계로 잘못 해석하지 않는지 확인
- 같은 그룹을 가리키는 여러 근거는 `resolved`, 서로 다른 그룹은 `conflict`가 되는지 확인
- 등록 정보와 폴더 정보가 없으면 `unknown`이고 피부과 기본값이 생기지 않는지 확인
- 사용자의 직접 변경값이 자동 판별값보다 우선하는지 확인

### 통합 테스트

- 연결된 고객 진료과가 있으면 사진작업실과 채팅 흐름이 선택 단계를 건너뛰는지 확인
- 폴더명과 정확히 일치하는 등록 고객의 진료과를 적용하는지 확인
- 재활의학과 폴더가 근골격·통증계로 자동 적용되는지 확인
- Bridge 계획이 진료과와 출처를 사진 분류에 전달하는지 확인
- 자동 출처 충돌 시 분석을 시작하지 않고 선택 UI를 표시하는지 확인
- 알 수 없는 진료과에서만 선택 UI가 나타나는지 확인
- NAS/원격 분류가 기존처럼 알 수 없는 진료과에서 작업 생성을 중단하는지 확인

### 회귀 및 화면 검증

- 기존 Bridge, 사진 분류, NAS 분류 테스트 실행
- 타입 검사, 변경 파일 린트, 전체 테스트와 프로덕션 빌드 실행
- 넓은 화면과 좁은 창에서 자동 적용 요약, `변경`, unknown/conflict 안내를 확인
- 실제 연결 고객과 폴더를 사용해 Bridge → Scene 검토 흐름에서 진료과가 다시 나타나지 않는지 확인

## 13. 인수 조건

- 등록된 정형외과·신경외과·마취통증의학과·재활의학과 고객은 사진 분류에서 모두 `근골격·통증계` 규칙을 자동 적용받는다.
- 자동 판별된 작업에서는 진료과 선택 화면이 반복 노출되지 않는다.
- Bridge에서 사진 분류로 이동해도 진료과와 판별 출처가 유지된다.
- 자동 적용된 값은 사용자가 `변경`을 눌러 수정할 수 있다.
- 알 수 없거나 충돌한 진료과는 임의 기본값으로 처리하지 않는다.
- 기존 DB 값, Worker payload, Scene 분류 결과와 파일 처리 동작을 손상하지 않는다.

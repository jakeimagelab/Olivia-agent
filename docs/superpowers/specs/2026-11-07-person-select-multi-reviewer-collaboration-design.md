# 사진선택 프로젝트 다중 검토자 협업 설계

작성일: 2026-11-07  
대상: Olivia-agent 최신 `main`

## 1. 목적과 범위

`access_mode = project_shared`인 사진선택 프로젝트를 여러 검토자가 동시에 사용하도록 확장한다. 관리자가 검토자를 등록하고 각자 전용 링크를 발급하며, 검토자별 사진 선택·별점·컬러 레이블·메모·제출 결과는 서로 독립적으로 저장한다. 프로젝트 참여자 모두가 대화할 수 있는 실시간 대화창과 관리자가 등록한 NAS 원본 링크를 여는 다운로드 기능을 함께 제공한다.

기존 개인별 로그인/PIN 프로젝트, 기존 classic 화면, 관리자 Olivia Bridge, 기존 프로젝트 사진과 선택 이력은 변경하거나 삭제하지 않는다.

## 2. 확정된 사용자 경험

### 2.1 검토자 초대

- 관리자는 프로젝트 설정에서 검토자 이름과 역할을 등록한다.
- 예: `정연호 / 대표`, `클라이언트 / 고객`, `매니저 / 진행`.
- 검토자마다 추측하기 어려운 고유 토큰을 가진 전용 링크를 발급한다.
- 링크는 개별적으로 비활성화·재발급할 수 있다.
- 공용 링크에서 이름을 고르는 방식은 사용하지 않는다. 다른 사람의 이름으로 접속하거나 결과를 덮는 위험을 막기 위해 링크 자체가 검토자 신원을 나타낸다.
- 검토자 링크에는 다른 검토자의 비공개 토큰이나 관리자 정보가 포함되지 않는다.

### 2.2 선택 수량

- 프로젝트 공용 방식은 사진 선택 장수 제한을 두지 않는다.
- 최소 한 장부터 해당 프로젝트에 등록된 모든 사진까지 제출할 수 있다.
- 관리자 설정의 카테고리별 `pick` 값은 공용 프로젝트의 선택 한도로 해석하지 않는다.
- 개인별 접근 방식은 기존 카테고리별 기본·추가 선택 제한을 유지한다.
- 요청 크기와 서비스 보호를 위한 기술적 최대 항목 수 검증은 유지하되, 사용자에게 제공하는 선택 장수 정책으로 노출하지 않는다.

### 2.3 별점과 컬러 셀렉

- `1~5`: 고객 별점 1~5를 적용한다.
- `6`: 빨강, `7`: 노랑, `8`: 초록, `9`: 파랑 컬러 레이블을 적용한다.
- 같은 컬러 키를 다시 누르면 해당 컬러 레이블을 해제한다.
- 별점과 컬러 레이블은 독립 상태이며 한 사진이 둘을 함께 가질 수 있다.
- `0`: 현재 작업 대상의 별점과 컬러 레이블을 모두 제거하여 고객 셀렉에서 제외한다.
- 사진 클릭은 포커스와 작업 대상만 바꾸며 별점·컬러·셀렉 수를 변경하지 않는다.
- 셀렉 사진은 별점 또는 컬러 레이블이 하나 이상 있는 사진의 합집합이다.
- 범위 선택, 영역 선택, 리뷰, 전체화면에서도 같은 키 규칙을 사용한다.

### 2.4 오른쪽 대화창

- 기존 오른쪽 영역은 `미리보기 | 대화` 두 개의 패널 서브탭으로 구성한다.
- 미리보기의 사진 비율, 별점·컬러·메모, 크게 보기 기능을 보존한다.
- 대화 탭은 프로젝트 단위의 공용 대화방이다. 검토자와 관리자가 같은 대화를 본다.
- 각 메시지에 작성자 이름·역할·작성 시각을 표시한다.
- 새 메시지가 오면 대화 탭에 읽지 않은 메시지 수를 표시한다.
- 텍스트 메시지를 우선 지원하며 첨부, 수정, 삭제, 멘션은 이번 범위에서 제외한다.
- 화면 뒤 배경 blur나 별도 팝업 대화창을 만들지 않는다.

### 2.5 NAS 원본 다운로드

- 관리자는 프로젝트 설정에 프로젝트 단위 NAS 원본 링크 하나를 입력한다.
- 링크는 `https` URL만 허용하고 서버에서 형식과 길이를 검증한다.
- 링크가 있을 때만 고객 Bridge에 `원본 다운로드` 버튼을 표시한다.
- 버튼은 관리자 입력 링크를 새 창으로 연다. 썸네일·미리보기 파일을 원본인 것처럼 다운로드하지 않는다.
- 앱 서버는 NAS 원본을 복제·프록시·ZIP 생성하지 않는다.
- NAS 인증과 접근 만료는 해당 NAS 공유 링크 정책을 따른다.

## 3. 데이터 구조

기존 테이블은 삭제하지 않고 additive migration으로 확장한다.

### 3.1 검토자

`person_select_shared_reviewers`

- `id uuid primary key`
- `event_id uuid not null`
- `display_name text not null`
- `role_label text not null default ''`
- `access_token_hash text not null unique`
- `token_version integer not null default 1`
- `active boolean not null default true`
- `last_seen_at timestamptz`
- `created_at`, `updated_at`

원문 토큰은 DB에 저장하지 않고 SHA-256 해시만 저장한다. 관리자가 링크를 재발급하면 토큰 버전을 올리고 이전 링크를 즉시 무효화한다.

### 3.2 검토자별 초안과 제출

기존 `person_select_shared_drafts`, `person_select_shared_selections`, `person_select_shared_selection_items`에 `reviewer_id` 소유관계를 추가한다.

- 초안 유일성: `(event_id, reviewer_id)`
- 제출 멱등성: `(event_id, reviewer_id, request_key)`
- 제출 항목에 `customer_rating smallint null`과 `customer_color_label smallint null`을 저장한다.
- 별점은 1~5, 컬러는 6~9만 허용한다.
- 사진별 메모는 기존 길이 제한을 유지한다.
- 각 API 요청은 검토자 토큰, 프로젝트, 이미지 소유관계를 모두 검증한다.

기존 이벤트 단위 공동 초안과 제출은 migration에서 자동 삭제하거나 임의로 특정 사람에게 합치지 않는다. 프로젝트마다 `기존 공동 셀렉`이라는 비활성화할 수 없는 호환 검토자 레코드를 만들고 기존 초안·제출의 `reviewer_id`를 그 레코드로 연결한다. 기존 관리자 조회와 RAW 매칭은 해당 결과를 계속 찾을 수 있다.

### 3.3 대화

`person_select_project_messages`

- `id uuid primary key`
- `event_id uuid not null`
- `reviewer_id uuid null` — 고객 검토자 메시지
- `admin_actor text null` — 관리자 메시지 표시명
- `body text not null`
- `client_request_id text not null`
- `created_at timestamptz not null`
- `(event_id, client_request_id)` unique

고객 API는 토큰에 연결된 `reviewer_id`를 서버가 직접 채운다. 요청 본문으로 작성자를 받지 않는다. 관리자는 기존 관리자 세션을 검증한 API를 사용한다. 메시지는 서비스 역할을 통한 최소 API에서만 읽고 쓰며, 테이블을 익명 사용자에게 직접 공개하지 않는다.

### 3.4 프로젝트 설정

`person_select_events`에 다음 설정을 추가한다.

- `nas_download_url text null`

검토자별 링크는 별도 검토자 테이블에서 관리한다. 기존 `shared_token`은 이전 공용 링크 호환과 프로젝트 식별에 유지한다.

## 4. API와 동시성

### 4.1 공개 검토자 API

검토자 전용 링크 토큰을 사용하는 최소 API를 둔다.

- 프로젝트·검토자·이미지 목록 조회
- 검토자별 초안 조회·저장
- 검토자별 최종 제출
- 메시지 목록 조회·전송
- 메시지 변경 이벤트 스트림
- 개별 이미지 만료 URL 갱신

모든 요청에서 토큰 해시, 활성 상태, 프로젝트 상태, 만료, 이미지 소유관계를 검증한다. 다른 검토자의 초안·제출은 공개 응답에 포함하지 않는다.

### 4.2 선택 저장 충돌

- 초안은 검토자별 revision을 사용한다.
- 같은 검토자가 두 기기에서 동시에 수정하면 revision 충돌을 반환하고 최신 상태를 다시 가져와 사용자에게 알린다.
- 다른 검토자는 서로 다른 초안 행을 쓰므로 충돌하지 않는다.
- 저장 중 다른 사진을 편집해도 늦은 응답이 새 편집 기준선을 덮지 않도록 클라이언트 edit version을 유지한다.
- 제출은 `request_key`로 멱등 처리한다.

### 4.3 실시간 대화

세 가지 방식 중 서버 검증 SSE를 사용한다.

1. 브라우저의 Supabase 직접 구독: 빠르지만 공개 검토자용 RLS/JWT 발급 범위가 커진다.
2. 짧은 주기 폴링: 단순하지만 메시지 지연과 불필요한 요청이 생긴다.
3. **서버 검증 SSE(채택)**: 검토자 토큰을 서버에서 검증한 뒤, 서버의 Supabase Realtime 구독을 변경 신호로 사용하고 클라이언트가 canonical 메시지 API를 다시 조회한다.

기존 Olivia 대화 이벤트 스트림 패턴을 재사용한다. 연결은 heartbeat와 자동 재연결을 지원하고, 스트림이 끊긴 경우 제한된 폴링으로 보완한다. Realtime payload 자체를 메시지 원본으로 사용하지 않아 중복·순서 오류를 막는다.

## 5. 화면 구조

### 5.1 고객 Bridge

- 왼쪽: 기존 폴더 탐색
- 중앙: 기존 썸네일 그리드
- 오른쪽: `미리보기 | 대화` 밑줄형 서브탭
- 하단: 전체 사진 수, 현재 검토자의 셀렉 수, 저장 상태, 리뷰, 최종 제출

오른쪽 미리보기에는 기존 별점 UI와 함께 네 개 컬러 레이블 버튼을 추가한다. 컬러는 관리자 Bridge의 `BRIDGE_COLOR_LABELS`를 재사용한다. 썸네일에는 별점과 컬러 표시를 각각 보여준다. 다른 검토자의 선택은 고객 화면에 섞지 않는다.

NAS 링크가 있는 경우 상단의 보조 동작으로 `원본 다운로드`를 제공한다. 최종 제출만 주 실행 오렌지 버튼으로 유지한다.

### 5.2 관리자 프로젝트 화면

- 검토자 추가, 이름·역할 수정, 링크 복사, 링크 재발급·비활성화
- 검토자별 접속 시각, 저장 상태, 제출 시각, 선택 장수
- 검토자별 결과 열기
- 선택 비교: 특정 검토자, 합집합, 전체 교집합, 검토자 간 차이
- 프로젝트 대화 확인과 관리자 메시지 전송
- NAS 원본 링크 입력·수정·제거

개인별 접근 방식 화면에는 이 검토자 관리 UI를 노출하지 않는다.

## 6. 관리자 Bridge와 RAW 매칭

- 관리자 선택 데이터와 각 검토자의 고객 선택 데이터는 독립적으로 유지한다.
- 고객 셀렉 불러오기에서 프로젝트와 검토자를 명시적으로 고른다.
- 여러 검토자의 결과를 자동으로 하나로 합치지 않는다.
- 관리자가 합집합·교집합 등 비교 집합을 선택한 뒤 기존 RAW 매칭 실행 흐름으로 넘긴다.
- 안정적인 이미지 ID와 상대경로를 우선 사용하며 basename 중복은 기존과 같이 확인 필요로 남긴다.

## 7. 보안과 데이터 보존

- 운영 사진, 기존 검토 결과, 참가자, 주문, 메모를 삭제하지 않는다.
- 원본 NAS 경로나 관리자 API를 공개 응답에 포함하지 않는다. 고객에게는 관리자가 명시적으로 입력한 공유 URL만 제공한다.
- 검토자 토큰은 충분한 난수로 생성하고 해시 저장한다.
- 메시지와 선택 API에 rate limit, 요청 크기, 메모 길이, 메시지 길이 검증을 적용한다.
- 비활성·재발급된 링크는 즉시 거부한다.
- 관리자용 API는 기존 관리자 인증을 유지한다.

## 8. 오류 처리

- 만료·비활성 링크: 링크가 사용할 수 없는 정확한 이유를 표시한다.
- 선택 revision 충돌: 입력을 버리지 않고 새로고침 필요 상태를 표시한다.
- 메시지 연결 끊김: 재연결 중 상태를 표시하고 전송 실패 메시지는 재시도할 수 있게 한다.
- NAS 링크 없음: 다운로드 버튼을 숨긴다.
- NAS 링크가 열리지 않음: 앱이 완료로 가장하지 않고 외부 공유 링크 문제임을 안내한다.
- 제출 실패: 현재 별점·컬러·메모를 유지한다.

## 9. 테스트 기준

### 9.1 선택

1. 프로젝트 공용 방식에서 카테고리 수량과 무관하게 전체 사진까지 선택 가능
2. 개인별 방식의 기존 선택 제한 유지
3. 정연호와 클라이언트의 별점·컬러·메모·제출이 서로 섞이지 않음
4. 숫자 1~5 별점, 6~9 컬러, 같은 컬러 키 토글, 0 전체 해제
5. 별점과 컬러를 함께 가진 사진이 셀렉 수에 한 번만 포함
6. 마우스 포커스·작업 대상 변경만으로 셀렉 데이터가 바뀌지 않음
7. 새로고침 후 검토자별 상태 복원
8. 같은 검토자 두 기기의 revision 충돌 처리
9. 제출 재시도 멱등 처리

### 9.2 대화

10. 두 검토자와 관리자가 동시에 접속해 새 메시지를 확인
11. 메시지 작성자가 서버가 확인한 검토자와 일치
12. 스트림 재연결 후 누락·중복 없이 canonical 목록 복원
13. 다른 프로젝트 메시지 접근 거부
14. 비활성 검토자 링크의 메시지 조회·전송 거부

### 9.3 다운로드와 회귀

15. NAS 링크가 있을 때만 원본 다운로드 표시
16. 관리자 입력 `https` 링크만 열림
17. 썸네일 URL을 원본 다운로드로 사용하지 않음
18. 기존 공동 셀렉 데이터가 호환 검토자 결과로 유지
19. 기존 개인별 PIN, classic 화면, 주문, RAW 매칭 정상

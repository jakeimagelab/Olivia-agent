# Olivia Agent PCRM 기반 구축 설계

작성일: 2026-07-25

## 1. 목표

기존 Olivia Agent의 고객관리와 고객 포털을 하나의 PhotoClinic CRM(PCRM) 흐름으로 연결한다.

- 관리자는 병원, 프로젝트, 승인 대기, 촬영 일정과 다음 업무를 한 화면에서 파악한다.
- 고객은 프로젝트 전용 링크로 접속해 현재 단계와 자신이 해야 할 일을 확인한다.
- 기존 견적, 계약, 콘티, 갤러리, 수정 요청, 리뷰, PER 기능을 폐기하거나 복제하지 않고 재사용한다.
- 1차에서는 실사용 가능한 기반과 핵심 연결을 완성하고, 입력 구조가 큰 기능은 후속 단계로 분리한다.

## 2. 확정된 디자인 기준

### 관리자 PCRM

사용자가 제공한 관리자 PCRM 참고 이미지를 화면 구조와 정보 밀도의 기준으로 삼는다.

- 좌측 딥그린 PCRM 사이드바
- 상단 PhotoClinic 로고, 페이지 정체성, 알림 및 관리자 정보
- 전체 고객, 진행 중 프로젝트, 고객 승인 대기, 관리자 작업 대기, 이번 주 촬영, 완료 프로젝트의 6개 요약 카드
- 최근 프로젝트 현황을 중심으로 한 테이블
- 승인 대기, 오늘 일정, 최근 활동, 최근 문의, PER 현황 카드
- 오렌지는 고객 등록, 승인 등 핵심 행동에만 사용

참고 이미지의 구조를 따르되 실제 구현 값은 반드시 `lib/theme.ts`의 `C`, `R`, `FS`, `SP`를 사용한다. 새로운 폰트나 색상 시스템, 외부 UI 라이브러리는 도입하지 않는다.

### 고객 PCRM

사용자가 제공한 고객 PCRM 참고 이미지처럼 상단형 포털 구조를 사용한다.

- PhotoClinic 로고와 고객 전용 포털 표기
- 병원과 프로젝트 선택
- 홈, 문서함, 진행현황, 촬영 준비, 콘티, 갤러리, 수정 요청, 리뷰, PER 메뉴
- 프로젝트 요약 히어로
- 가장 중요한 고객 행동을 우측 또는 상단의 오렌지 CTA로 강조
- 진행 과정, 승인 항목, 자료, 최근 갤러리, 일정, 담당자 메모, 문의, PER을 간결한 카드로 구성

관리자 화면보다 단순하고 고객이 5초 안에 다음 행동을 이해할 수 있어야 한다.

### 반응형

- 데스크톱: 참고 이미지의 다열 대시보드와 우측 액션 영역 유지
- 태블릿: 2열 또는 1열로 재배치
- 모바일: 카드 1열, 메뉴 가로 스크롤, 최소 44px 터치 영역
- 고정 폭과 페이지 가로 스크롤 금지

## 3. 기존 구조 분석 결과

- `app/(client-hub)/clients/page.tsx`에는 고객 목록, 생성, 상세, 워크플로우, 문서, 포털 기능이 한 파일에 혼재한다.
- `WorkflowBar.tsx`, `ConsultMeetingForm.tsx`는 재사용 가능한 기존 기능이다.
- `workflow_runs`는 이미 한 고객의 복수 실행을 저장하므로 PCRM 프로젝트의 기준 엔티티로 확장할 수 있다.
- 현재 고객 생성 API는 고객 등록과 워크플로우 생성을 동시에 수행한다. 새 구조에서는 고객 저장과 프로젝트 생성을 분리해야 한다.
- 기존 고객 포털은 토큰을 검증하지만 `client_id` 기준이며, 접속 시 최신 워크플로우를 선택한다.
- 견적, 계약, 콘티, 갤러리, 수정 요청, 리뷰, PER, 워크플로우 산출물과 승인 데이터가 이미 존재한다.
- 기존 포털 대시보드와 갤러리, 수정 요청, 리뷰, PER 페이지는 유지하며 공통 셸과 프로젝트 범위를 개선한다.
- 고객 포털 이벤트와 내부 에이전트 로그가 나뉘어 있으므로 PCRM 활동 타임라인에서 일관되게 조회할 계층이 필요하다.

## 4. 데이터 모델 결정

### 기존 엔티티 재사용

- `clients`: 병원 고객 마스터
- `workflow_runs`: 고객별 PCRM 프로젝트
- `workflow_artifacts`: 견적, 계약, 콘티, 납품 등 프로젝트 자료
- `agent_approvals`: 기존 내부 승인 및 대기 상태
- 기존 quotes, contracts, conti, gallery, revision, review, PER 관련 테이블과 API

별도 `pcrm_projects` 테이블을 만들지 않는다. 프로젝트 원본이 둘로 나뉘어 동기화 오류가 생기는 것을 막기 위해 `workflow_runs`를 확장한다.

### additive migration

기존 데이터를 삭제하거나 재생성하지 않는다. 실제 스키마 확인 후 필요한 필드만 추가한다.

- `client_portal_access.workflow_run_id`: 프로젝트별 포털 접근 범위
- `workflow_runs`: 프로젝트명, 유형, 촬영 유형, 담당자, 시작일, 예정 완료일, 계약 예정 금액, 메모 등에 필요한 누락 필드
- `pcrm_publications`: 기존 결과물의 고객 공개, 열람, 승인, 수정 요청 상태를 통합 관리
- `pcrm_activity_logs`: 관리자, 고객, 시스템의 주요 프로젝트 활동 기록

`pcrm_publications`는 원본 견적·계약·콘티·갤러리를 복제하지 않고 `related_type`, `related_id`로 연결한다.

상태 흐름:

`draft → internal_review → published → viewed → revision_requested | approved → completed → archived`

### 기존 링크 호환

- 새 링크는 `client_id`와 `workflow_run_id` 모두에 연결한다.
- 기존 고객 단위 링크는 계속 허용하고 서버에서 최신 활성 프로젝트를 선택한다.
- 새로 발급되는 링크는 프로젝트별 권한을 기본으로 한다.

## 5. 관리자 PCRM 정보 구조

기존 `/clients` 경로는 유지하고 화면 명칭을 `PCRM · 고객 및 프로젝트 관리`로 통일한다.

### 목록

- 6개 요약 카드
- 병원명, 원장명, 담당자, 진료과 검색
- 프로젝트 상태, 워크플로우 단계, 승인 대기, 촬영 예정일 필터
- 데스크톱에서는 밀도 높은 프로젝트 테이블
- 모바일에서는 카드 목록
- 고객 상세, 프로젝트 열기, 포털 열기, 링크 복사, 프로젝트 생성 액션

### 고객 등록

고객 저장만 수행하며 워크플로우를 자동 시작하지 않는다. 저장 후 다음 선택지를 제공한다.

- 프로젝트 생성
- 상담 기록 작성
- 프로젝트용 포털 링크 생성
- 고객 상세로 이동

### 고객 상세

- 고객 헤더와 프로젝트 선택기
- 새 프로젝트 생성
- 실제 `workflow_run`을 사용하는 진행 표시
- 개요, 상담 기록, 견적·계약, 촬영 준비, 콘티, 일정, 갤러리, 수정·승인, 납품, 리뷰, PER, 활동 기록 탭

1차 개요 화면 우선순위:

1. 다음 해야 할 일
2. 고객 승인 대기
3. 관리자 작업 대기
4. 현재 단계
5. 최근 활동
6. 촬영 일정
7. 담당자 메모
8. 프로젝트 자료
9. 포털 상태

현재 `clients/page.tsx`의 동작을 보존하면서 목록, 생성, 상세, 프로젝트, 포털, 활동 컴포넌트로 점진 분리한다.

## 6. 고객 PCRM 정보 구조

`PortalShell`과 현재 토큰 기반 세션을 재사용한다.

### 공통 셸

- PhotoClinic 로고
- 고객 전용 PCRM 표기
- 병원명과 프로젝트 선택
- 담당 매니저
- 프로젝트에서 공개된 기능만 표시하는 메뉴

### 홈

1. 프로젝트 요약
2. 지금 해야 할 일
3. 고객용 10단계 진행 과정
4. 확인 및 승인 항목
5. 프로젝트 자료
6. 최근 갤러리
7. 담당자 메모
8. 촬영 일정
9. 문의
10. PER

내부 워크플로우 단계는 고객에게 직접 노출하지 않는다. `lib/pcrm/clientWorkflow.ts`의 순수 함수가 내부 단계를 고객용 10단계, 진행률, 다음 행동, 메뉴 공개 여부로 변환한다.

### 프로젝트 범위

모든 고객용 API는 토큰으로 `client_id`와 `workflow_run_id`를 서버에서 결정한다. 요청 본문의 식별자만 믿고 데이터를 조회하지 않는다.

## 7. 공개·승인·활동 흐름

관리자가 결과물을 만들었다고 자동 공개하지 않는다.

1. 관리자가 기존 자료를 프로젝트에 연결
2. 내부 확인
3. 고객 공개
4. 고객 열람 시 `viewed_at` 기록
5. 고객 승인 또는 수정 요청
6. 관리자 화면 즉시 재조회
7. 다음 행동과 워크플로우 상태 재계산
8. 모든 단계에 활동 기록 생성

승인, 공개, 수정 요청 버튼은 저장 중 비활성화하고 서버에서 현재 상태를 다시 검증해 중복 실행을 방지한다.

## 8. 보안

- 포털 토큰은 긴 난수이며 원본 ID를 URL에 노출하지 않는다.
- 서버에서 활성 여부와 만료 시간을 검증한다.
- 토큰에 연결된 고객과 프로젝트 밖의 조회를 차단한다.
- 관리자 API는 기존 인증을 유지한다.
- 서비스 역할 키는 서버에서만 사용한다.
- 신규 테이블은 RLS를 활성화하고 기존 서버 접근 패턴에 맞춘다.
- 접근, 열람, 승인, 수정 요청을 감사 가능한 활동으로 남긴다.

## 9. 1차 구현 범위

이번 구현에서 우선 완성할 범위:

1. 프로젝트 단위 포털 토큰과 권한 기반
2. 관리자 PCRM 대시보드와 고객·프로젝트 목록
3. 고객 등록과 프로젝트 생성을 분리
4. 복수 프로젝트 생성 및 전환
5. 관리자 고객 상세 개요
6. 고객 PCRM 공통 셸과 홈 대시보드
7. 내부 워크플로우의 고객용 단계 매핑
8. 기존 견적, 계약, 콘티, 갤러리, 수정, 리뷰, PER 상태 연결
9. 프로젝트 활동 기록
10. 모바일·태블릿 반응형

후속 단계:

- 문서 버전별 공개·승인·피드백의 전체 편집 UI
- 촬영 준비 항목의 상세 활성화와 고객 입력
- 콘티 장면별 피드백과 첨부
- PCRM 내부 문의함
- 내부 갤러리 선택 고도화
- 전자서명 공급자 연동

후속 기능을 위한 데이터 경계를 막지 않지만, 1차 완료로 가장하지 않는다.

## 10. 검증

### 기능

- 고객 등록만으로 프로젝트가 자동 생성되지 않는다.
- 한 고객에게 여러 프로젝트를 만들고 전환한다.
- 프로젝트별 포털 링크를 만들고 복사·비활성화·재발급한다.
- 고객 홈에 현재 프로젝트와 다음 행동이 표시된다.
- 기존 견적, 계약, 콘티, 갤러리 기능이 유지된다.
- 공개된 자료만 고객에게 표시된다.
- 고객 행동이 관리자 화면과 활동 기록에 반영된다.

### 보안

- 만료 또는 비활성 링크 접근 차단
- 고객 A 토큰으로 고객 B 데이터 조회 차단
- 같은 고객의 다른 프로젝트도 토큰 범위 밖이면 차단
- 중복 승인과 중복 수정 요청 방지

### 품질

- `npm run typecheck`
- 관련 테스트
- `npm run build`
- 데스크톱, 태블릿, 모바일 브라우저 확인
- 주요 화면 가로 스크롤과 콘솔 오류 확인

## 11. 비목표

- 기존 기능의 전면 재작성

- 고객용 실시간 채팅 시스템
- 데모 데이터만 사용하는 화면

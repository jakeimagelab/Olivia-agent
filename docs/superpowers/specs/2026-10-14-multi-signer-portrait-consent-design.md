# 초상권 동의서 다중 서명 설계

작성일: 2026-10-14

## 1. 목표

- 하나의 초상권 동의서 링크로 여러 사람의 서명을 각각 받는다.
- 동의서마다 받을 인원을 지정하고, 완료 인원과 목표 인원을 `1/2명`처럼 표시한다.
- 기존에 받은 서명과 기존 공개 링크를 보존한다.
- 데스크탑 OS의 초상권 동의서 앱에서 서명 결과를 바로 확인하고 사람별 PDF를 내려받는다.
- IP 주소는 증빙 정보로만 보관하며 서명자 식별이나 화면 분기에 사용하지 않는다.

## 2. 범위 밖

- 본인 인증, 휴대폰 인증, 전자서명 인증기관 연동은 추가하지 않는다.
- 서명 완료 기록의 관리자 삭제·수정 기능은 만들지 않는다.
- 고객·촬영 건 연결 방식과 기존 공개 경로 `/portrait-consent/[token]`은 바꾸지 않는다.
- 기존 서명 데이터 열은 즉시 삭제하지 않는다. 호환성과 안전한 전환을 위해 남긴다.

## 3. 현재 문제

현재 `portrait_consents` 한 행이 동의서 양식, 공유 토큰, 서명자 이름, 서명 이미지와 동의 결과를 모두 가진다. 첫 제출이 들어오면 부모 행의 상태가 `signed`로 바뀌어 같은 링크의 다음 제출을 거절한다.

데스크탑 앱은 화면을 처음 열 때 목록을 불러온 뒤 공개 서명 완료를 자동으로 다시 확인하지 않는다. 따라서 앱을 열어둔 상태에서는 제출 결과가 보이지 않을 수 있다.

## 4. 데이터 구조

### 4-1. 부모 동의서

기존 `portrait_consents`는 공통 양식과 공유 링크를 보관하는 부모 문서로 유지한다.

- `signature_limit integer not null default 1`
- 허용 범위는 `1~100`명이다.
- 완료 수가 목표보다 작으면 공유 링크가 유효한 동안 추가 서명을 받을 수 있다.
- 완료 수가 목표에 도달하면 상태를 `signed`로 바꾸고 자동 마감한다.
- 관리자가 목표 인원을 완료 수보다 크게 올리면 상태를 `sent`로 되돌려 다시 받을 수 있다.
- 목표 인원은 현재 완료 수보다 작게 줄일 수 없다.

부모 행의 기존 `provider_name`, `signature_data_url`, `consent_shoot`, `consent_usage`, `signed_date`, `signed_at` 열은 마이그레이션 후에도 남긴다. 새 제출은 이 열에 쓰지 않고 새 서명 테이블에만 저장한다.

### 4-2. 서명 기록

새 테이블 `portrait_consent_signatures`를 만든다.

| 열 | 역할 |
|---|---|
| `id` | 서명 기록 UUID |
| `portrait_consent_id` | 부모 동의서, 삭제 시 함께 삭제 |
| `consent_shoot` | 촬영 동의 여부 |
| `consent_usage` | 홍보 목적 사용 동의 여부 |
| `provider_name` | 초상권 제공자 이름 |
| `signature_data_url` | 서명 이미지 원본 |
| `signed_date` | 문서 표시용 작성일 |
| `signed_at` | 서버 기준 제출 시각 |
| `signer_ip` | 증빙용 접속 IP, nullable |
| `user_agent` | 증빙용 브라우저 정보, nullable |
| `created_at` | 생성 시각 |

`portrait_consent_id, signed_at desc` 인덱스를 추가하고 서비스 역할만 접근하게 한다.

### 4-3. 기존 서명 이전

기존 `status = 'signed'` 행은 서명 테이블로 한 번만 옮긴다.

- 이전 서명 기록의 `id`는 부모 동의서 `id`와 같게 넣어 마이그레이션을 반복해도 중복되지 않게 한다.
- 기존 이름, 동의 결과, 서명 이미지, 작성일과 제출 시각을 그대로 복사한다.
- 해당 부모의 `signature_limit`은 기본값 1이므로 이전 직후 `1/1명 완료` 상태다.
- 사용자가 목표를 2명으로 바꾸면 `1/2명 완료`로 다시 열리며, 토큰이 만료·취소되지 않았다면 기존 URL을 그대로 쓴다.
- 기존 토큰이 만료되거나 취소된 경우에는 새 링크 발급이 필요하며 URL도 새로 만들어진다.

## 5. 공개 링크 동작

### 5-1. 조회

`GET /api/portrait-consent/[token]`은 공통 양식과 아래 상태만 반환한다.

- `signatureCount`
- `signatureLimit`
- `canSign`

다른 서명자의 이름, 동의 결과, 서명 이미지는 절대 반환하지 않는다.

- `canSign = true`이면 항상 빈 서명 폼을 보여준다.
- 목표 인원에 도달했으면 `서명이 모두 완료되었습니다` 화면을 보여준다.
- 만료·취소된 토큰은 기존 오류 응답을 유지한다.

### 5-2. 제출

`POST /api/portrait-consent/[token]`은 기존 입력 검증 후 DB 함수로 제출한다.

DB 함수는 부모 행을 잠근 뒤 현재 서명 수를 다시 세고 다음을 한 트랜잭션에서 처리한다.

1. 목표 인원 미달 여부 확인
2. 사람별 서명 기록 삽입
3. 새 완료 수 계산
4. 목표 도달 시 부모 상태를 `signed`, 미달이면 `sent`로 갱신

동시에 두 사람이 제출해도 목표 인원을 초과하지 않는다. 이미 마감된 경우 `필요한 서명이 모두 제출되었습니다.`를 반환한다.

응답에는 방금 제출한 사람의 서명 기록만 반환한다. 공개 링크에서 기존 다른 사람의 서명 정보는 노출하지 않는다.

### 5-3. 제출 완료 화면

- `1/2명이 서명했습니다`처럼 진행 상태를 보여준다.
- 본인 제출 결과와 본인 보관용 PDF 다운로드를 제공한다.
- 목표에 아직 도달하지 않았으면 보조 버튼 `다른 사람 서명하기`를 표시한다.
- 이 버튼은 이름, 동의 선택, 캔버스를 비우고 같은 링크의 새 입력 화면을 연다.
- 목표에 도달했으면 추가 서명 버튼을 표시하지 않는다.

## 6. 데스크탑 OS 관리 화면

기존 왼쪽 목록 / 오른쪽 작성 구조를 유지한다.

### 6-1. 왼쪽 목록

- 각 동의서 행에 `서명 1/2` 진행 상태를 표시한다.
- 검색은 제목, 고객, 촬영 건과 서명자 이름을 포함한다.
- 상태는 `초안`, `전달됨`, `서명 완료`를 유지한다.
- `서명 완료`는 완료 수가 목표 인원에 도달한 문서다.

### 6-2. 오른쪽 상세

- 링크 발급 전 또는 서명 0명일 때는 기존 작성 폼을 보여준다.
- 한 명이라도 서명한 뒤에는 서명 당시 양식을 보존하기 위해 본문 편집을 잠근다.
- 상단에 목표 인원 입력과 `1/2명 완료` 진행 상태를 보여준다.
- 서명자 목록은 가로 행으로 표시한다. 이름, 제출 시각, 동의 결과를 읽는 순서대로 배치한다.
- 서명자 행을 선택하면 해당 사람의 서명 원본을 오른쪽 상세에 표시한다.
- `PDF 다운로드`는 선택한 서명자의 문서를 만든다.
- 고객·촬영 건 연결 변경은 기존처럼 허용한다.
- 서명 기록은 관리자 화면에서도 수정하거나 삭제하지 않는다.

밝은 문서·폼 화면을 유지한다. 주 실행은 링크 발급 또는 저장 중 현재 맥락의 한 개만 주황 채움으로 두고, PDF·새로고침·연결 변경은 초록 외곽선 보조 버튼으로 둔다. 글자 굵기는 600을 넘기지 않는다.

### 6-3. 새 결과 자동 확인

- 앱이 보이는 동안 15초마다 목록과 선택 문서의 서명 목록을 다시 확인한다.
- 브라우저 창이 다시 활성화되거나 문서 탭이 다시 보이면 즉시 갱신한다.
- `새로고침` 보조 버튼도 제공한다.
- 갱신 실패 시 기존 결과를 지우지 않고 오류 문구를 남긴다.

## 7. 관리자 API

- 목록 API는 `signature_count`, `signature_limit`, 최근 서명자 정보를 함께 반환한다.
- 상세 API는 부모 양식과 서명 수를 반환한다.
- 새 `GET /api/conti/portrait-consents/[id]/signatures`는 해당 동의서의 서명 기록을 최신순으로 반환한다.
- 부모 PATCH는 `signatureLimit` 변경을 받는다.
- 본문 수정 잠금 기준은 부모 `status === 'signed'`가 아니라 `signature_count > 0`으로 바꾼다.
- 목표 인원을 늘릴 때 기존 토큰이 유효하면 토큰을 바꾸지 않는다.
- 기존 링크 재발급 API는 명시적으로 재발급할 때만 새 토큰을 만들며, 이전 토큰은 더 이상 유효하지 않다.

## 8. 개인정보와 오류 처리

- 접속 IP와 사용자 에이전트는 증빙 정보이며 서명자 식별, 중복 판정, 화면 분기에 사용하지 않는다.
- 공개 API는 다른 서명자의 개인정보를 반환하지 않는다.
- 토큰 만료, 토큰 취소, 목표 인원 완료, 잘못된 서명 데이터는 서로 다른 오류 문구로 구분한다.
- 서명 저장이 실패하면 부모 완료 수와 상태도 바뀌지 않는다.
- 데스크탑 갱신 실패는 기존 화면을 유지하고 재시도할 수 있게 한다.

## 9. 테스트

### 마이그레이션

- 기존 단일 서명이 사람별 서명 기록 한 건으로 이전된다.
- 마이그레이션을 반복해도 중복 기록이 생기지 않는다.
- 기존 토큰 해시와 만료 시각이 바뀌지 않는다.

### 공개 API

- 0/2에서 첫 제출 후 1/2와 `sent`가 된다.
- 1/2에서 두 번째 제출 후 2/2와 `signed`가 된다.
- 2/2에서 세 번째 제출은 거절된다.
- 동시 제출에서도 목표 인원을 넘지 않는다.
- 공개 GET이 다른 사람의 이름과 서명을 반환하지 않는다.
- 만료·취소 링크의 기존 동작을 유지한다.

### 관리자 API와 화면

- 기존 서명 완료 문서를 2명으로 늘리면 1/2로 다시 열린다.
- 완료 수보다 작은 목표 인원은 거절된다.
- 첫 서명 후 본문 수정은 거절되고 고객·촬영 건 연결은 가능하다.
- 데스크탑 목록에 진행 수가 표시되고 서명자별 원본·PDF를 확인할 수 있다.
- 포커스 복귀와 주기 갱신 후 새 서명이 화면에 반영된다.
- 넓은 폭과 좁은 폭에서 목록, 서명자 목록, 상세 전환을 확인한다.

## 10. 완료 기준

- 한 링크로 지정한 인원만큼 서로 독립된 서명을 받는다.
- 기존 첫 서명이 손실되거나 덮어써지지 않는다.
- 다른 서명자의 정보가 공개 링크에 노출되지 않는다.
- 두 번째 서명 직후 데스크탑 OS에서 `2/2명 완료`와 두 서명자 원본을 확인한다.
- 목표 도달 후 같은 링크의 추가 제출이 원자적으로 차단된다.
- 타입 검사, 관련 린트, 단위 테스트, 전체 Vitest, 프로덕션 빌드와 브라우저 화면 검증이 통과한다.

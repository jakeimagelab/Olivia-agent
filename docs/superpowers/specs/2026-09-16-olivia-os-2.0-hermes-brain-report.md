## 1. 기존 구조 분석

바로 구현에 들어가지 않고 4개 영역을 병렬로 조사했다. 핵심 결론: **요청서가 그리는 목표의
상당 부분이 이미 구현되어 라이브로 동작 중이었다.** 요청서를 "0부터 만드는 작업"으로
읽으면 안 되고, "이미 있는 걸 다시 만들지 않고 구조를 정리·강화하는 작업"으로 읽어야 했다.

### 1-1. Brain 아키텍처 (기존)

- `OLIVIA_AGENT_ENGINE`(`legacy`|`hermes`, `lib/hermes/client.ts:25`)이 이미 브레인 선택
  스위치이고, `.env.local`에 이미 `hermes`가 기본값으로 설정돼 있었다.
- 사용자 메시지의 실제 경로는 `app/api/olivia/v2/stream/route.ts` 하나다:
  - `useHermes`가 true면 `runHermesChat()`(`lib/hermes/client.ts`)이 Hermes 서버
    (`HERMES_BASE_URL`)에 SSE로 요청을 보낸다.
  - Hermes는 필요한 Tool을 **자기 쪽에서 판단해** Olivia의 MCP 서버
    (`app/api/hermes/mcp/route.ts` → `createOliviaHermesMcpServer()`)를 호출해 실행하고,
    Tool 결과까지 반영한 최종 텍스트를 돌려준다 — 즉 "Tool 실행 후 Brain이 재검토"(§11)가
    이미 Hermes MCP 루프 자체의 동작 방식이다.
  - Hermes 호출이 실패하면(`isHermesFallbackSafe`) 같은 라우트 안에서
    `activeAgentEngine = "legacy"`로 전환해 OpenAI Responses API 루프(같은 파일 내,
    `OLIVIA_V2_TOOLS` function-calling)로 폴백한다.
  - 이와 별도로 **완전히 다른, 더 오래된 Claude 기반 경로**
    (`lib/assistant/core/legacyOliviaCore.ts`)가 `/api/olivia`, `/api/olivia/stream`으로
    지금도 살아있다 — 주로 Telegram 채널이 사용한다.

### 1-2. Action Registry / Policy (기존)

- `lib/assistant/actions/*`(registry.ts/dispatcher.ts/permissions.ts/confirmations/audit/
  validation/security)는 **역할·승인·검증·rollback까지 완비된 프레임워크**지만,
  **프로덕션에서 단 한 번도 인스턴스화되지 않은 죽은 코드**였다(테스트에만 존재).
- 실제 살아있는 "Tool Registry"는 `lib/olivia/v2/toolExecutor.ts`의
  `OLIVIA_V2_TOOLS`(180+개 함수 스키마) + `DOMAIN_EXECUTORS`/`TOOL_ROUTER`다. 이걸
  `lib/hermes/mcp/oliviaToolBridge.ts`가 그대로 MCP Tool 목록으로 노출한다
  (`lib/hermes/mcp/exposurePolicy.ts`가 open/approval/blocked 3단계로 걸러서).
- `lib/hermes/mcp/registerXxxTools.ts` 여러 개(registerConti/Work/Quote/...)는
  `mcpServer.ts` 안 주석에 "롤백 비교용으로만 남기며 실제 endpoint에서는 호출하지 않는다"고
  명시된 **죽은 코드**다.

### 1-3. Memory (기존)

- `olivia_agent_memory` 테이블 + `lib/olivia/memory/{types,repository,format,executionPolicy}.ts`가
  이미 매 채팅 메시지마다 동작 중이다("앞으로 이렇게 해" → `save_agent_memory` → 다음 메시지
  system prompt에 `<taught_business_rules>`로 주입).
- `olivia_knowledge_patches`(관리자 큐레이션), `conti_case_documents/scenes`(벡터 RAG 콘티
  사례 라이브러리)도 이미 있다. **새 스키마를 만들 필요가 없었다.**

### 1-4. Conti 파일럿 (기존)

- `conti_v2` 9개 Tool이 이미 `OLIVIA_V2_TOOLS`를 통해 Hermes에 노출돼 있다 — 즉 Hermes가
  오늘도 콘티를 만들 수 있다.
- "어떤 Scene을 넣을지"는 약 80%가 코드(진료과 taxonomy, `lib/conti/departmentTaxonomy.ts`
  + `generate.ts`의 결정론적 스켈레톤 생성)이고, 20%가 선택적 AI 보강
  (`lib/conti/aiEnrichment.ts`, 문구/순서만 다듬음, Scene 추가·삭제 불가). 요청서 §15가
  원하는 "코드는 구조/CRUD, Hermes는 촬영 내용 판단" 분업이 이미 상당 부분 맞아떨어져 있었다.

## 2. 변경된 아키텍처

위 1번에서 확인한 "이미 있는 것"은 다시 만들지 않았다. 실제로 부족했던 부분만 골랐다:

1. Hermes 호출이 라우트 안에 `runHermesChat()` 직접 호출로 박혀 있어 `OliviaBrain` 같은
   이름 있는 계약이 없었다 → `lib/assistant/brain/` 추가, 호출부만 교체.
2. `exposurePolicy.ts`의 open/approval/blocked가 요청서의 READ/WRITE_SAFE/WRITE_IMPORTANT/
   DANGEROUS 4단계와 매핑되지만, DANGEROUS(파일 삭제류)가 **이름 기반으로 자동 차단되는
   장치가 없었다** → 패턴 기반 하드 가드 추가.
3. Memory는 "가르치면 즉시 적용"만 있고 "Hermes가 제안 → 사람이 승인"하는 단계가 없었다
   (§9) → 기존 테이블에 상태를 하나 더 얹어(새 테이블 없이) 추가.

```
[변경 전]                                  [변경 후]
UI → stream route                          UI → stream route
       → runHermesChat() 직접 호출                → hermesProvider.chat()  (OliviaBrain 구현체)
       → (실패시) OpenAI 루프                       → (실패시) OpenAI 루프  ※그대로, 미추출(아래 §13)

exposurePolicy: open/approval/blocked      exposurePolicy: 동일 3단계 + DANGEROUS_NAME_PATTERN
                                            (이름 패턴 매칭시 무조건 blocked, 목록 등록 여부와 무관)

save_agent_memory → 즉시 적용               save_agent_memory → 즉시 적용 (그대로, 유저가 이미 신뢰)
                                            + propose_agent_memory_rule → rule_candidate(비활성)
                                            + approve_agent_memory_rule(승인 카드 필요) → 승격
```

## 6. Hermes 연결 경로

```
사용자 메시지
  → app/api/olivia/v2/stream/route.ts
  → hermesProvider.chat()  (lib/assistant/brain/hermesProvider.ts)
  → runHermesChat()        (lib/hermes/client.ts, 미변경)
  → POST {HERMES_BASE_URL}/v1/chat/completions (SSE)
  → Hermes 서버가 필요하면 Olivia MCP 서버 호출
      app/api/hermes/mcp/route.ts → createOliviaHermesMcpServer()
      → attachOliviaToolBridge() → OLIVIA_V2_TOOLS 중 비차단 Tool만 노출
      → runTool() → DOMAIN_EXECUTORS → 실제 도메인 executor 실행
  → Hermes가 Tool 결과를 반영한 최종 텍스트로 응답
  → hermesProvider가 BrainChatResult{type:"message"}로 변환
  → route.ts가 UI action 해석 + SSE 전송 + 대화 저장 (미변경)
```

실패 시: `HermesChatError` → `hermesProvider`가 `BrainUnavailableError`로 재던짐 →
`isBrainFallbackSafe()`가 true(연결 전 실패)면 `activeAgentEngine="legacy"`로 전환해
같은 라우트 안의 OpenAI 루프로 폴백. false(스트림 시작 후 실패)면 사용자에게 이미 부분
출력이 나간 상태라 폴백하지 않고 에러를 그대로 던진다(이중 응답 방지, 기존 동작 유지).

## 7. Tool 호출 흐름

변경 없음 — `OLIVIA_V2_TOOLS`(스키마) → `oliviaToolBridge.ts`(MCP 노출, 정책 필터) →
`runTool()`/`DOMAIN_EXECUTORS`(dispatch) → 도메인 executor(`lib/olivia/v2/toolExecutors/*.ts`)
→ 실제 DB/파일 작업. 이번 작업은 이 파이프라인 위에 **새 도구 2개**(propose/approve
memory rule)만 추가했고, dispatch 메커니즘 자체는 손대지 않았다.

## 8. Policy 구조

`lib/hermes/mcp/exposurePolicy.ts`:

| 요청서 티어 | 코드 매핑 |
|---|---|
| READ | `getHermesToolMode()` → `"read"` (자동 실행) |
| WRITE_SAFE | policy `"open"` + mode `"mutation"` (자동 실행) |
| WRITE_IMPORTANT | `APPROVAL_TOOLS`(policy `"approval"`) — 승인 카드 필요 |
| DANGEROUS | `BLOCKED_TOOLS` ∪ `DANGEROUS_NAME_PATTERN` 매칭 — Hermes에 노출 자체가 안 됨 |

`DANGEROUS_NAME_PATTERN`은 `delete`/`raw`/`file`/`photo`/`document`/`shell`/
`system_config`/`format_disk` 조합을 정규식으로 잡는다. **오늘 등록된 Tool 중 이 패턴에
걸리는 건 0개**(회귀 테스트로 고정) — 실질적 방어선은 애초에 파일 삭제/RAW 이동 Tool이
존재하지 않는다는 것과, 사진 파이프라인의 실제 파일 조작이
`lib/photo-classifier/node/pathSafety.ts`/`sourceProjectPrep.ts`의 filesystem 가드로
막혀 있다는 것(Prompt가 아니라 코드 레벨, §7 요구사항)이다. 이 패턴은 **앞으로 누군가
실수로 위험한 이름의 Tool을 등록해도 자동으로 걸러지는 두 번째 방어선**이다.

## 9. Memory 구조

새 테이블 없음(요청서 §10 "기존 구조 재사용" 원칙). `olivia_agent_memory`의
`memory_type` enum에 `"rule_candidate"` 1개만 추가했다:

```
Hermes가 반복 패턴 관찰
  → propose_agent_memory_rule(key, proposedType, proposedValue, reason)
  → memory_type="rule_candidate"로 저장 (resolveExecutionPolicy가 이 타입을 모르므로 즉시 비활성)
  → 사용자에게 "공식 규칙으로 등록할까요?" 노출 (APPROVAL_TOOLS라 자동 실행 안 됨)
  → 사용자 승인
  → approve_agent_memory_rule(key)
  → memory_type이 proposedType(business_rule 등)으로 승격 + is_active=true
  → 다음 메시지부터 resolveExecutionPolicy가 정상 인식 + system prompt 주입
```

기존 `save_agent_memory`(사용자가 채팅으로 직접 가르치는 경로)는 **동작을 바꾸지
않았다** — 이미 신뢰받고 있는 기능이라 승인 게이트를 강제로 끼워넣지 않았다. 새 승인
경로는 "Hermes가 스스로 패턴을 발견해 제안"하는 경우에만 쓰인다.

## 10. Legacy fallback 방식

- `OLIVIA_AGENT_ENGINE=legacy`(또는 미설정)면 애초에 Hermes를 호출하지 않고 OpenAI 루프로
  직행 — 변경 없음.
- `OLIVIA_AGENT_ENGINE=hermes`인데 Hermes가 연결 전에 실패하면, 같은 요청 안에서
  OpenAI 루프로 자동 전환 — 변경 없음(호출 지점만 `isBrainFallbackSafe`로 교체).
- 완전히 별개로, `/api/olivia`·`/api/olivia/stream`(Telegram 등)은 여전히
  `legacyOliviaCore.ts`(Claude)로 direct 경로 — 이번 작업과 무관, 손대지 않음.

## 13. 아직 남은 문제

1. **FallbackProvider 미추출.** `app/api/olivia/v2/stream/route.ts`의 OpenAI Responses
   API 루프(약 300줄)는 SSE `send()`/대화 저장/pending action 상태 등 라우트 로컬 클로저와
   깊게 얽혀 있어, 이번 phase에서 `OliviaBrain` 인터페이스 뒤로 추출하지 않았다. 실제
   fallback 동작은 지금도 정상이지만(라우트 안 `activeAgentEngine="legacy"` 분기), 구조상
   `OliviaBrain`의 두 번째 구현체가 아직 없다. 살아있는 채팅 스트리밍을 건드리는 작업이라
   신중하게 별도 작업으로 진행하길 권장한다.
2. `app/api/hermes/chat/route.ts`, `lib/voice/summarizer.ts`도 `runHermesChat()`을 직접
   호출한다 — 이번엔 Olivia의 "메인 Brain 경로" 하나만 `OliviaBrain`으로 옮겼다. 나머지
   두 곳도 옮길지는 각각의 용도(범용 API vs 음성 요약 fallback)를 고려해 별도 판단 필요.
3. `lib/assistant/actions/*`(권한/승인/감사 프레임워크)는 여전히 미사용 상태로 남아있다.
   완비된 구조라 아깝지만, `legacyOliviaCore.ts`가 이미 그 일부(email.ts, confirmations,
   audit)를 쓰고 있어서 "Hermes MCP Tool이 이 프레임워크를 통과하게 만들기"는 상당한
   설계 결정이 필요한 별도 작업이다(예: 모든 WRITE_IMPORTANT Tool을
   `dispatchAssistantAction()`을 거치게 할지).
4. Multi-step 계획(§12, "촬영 정리하고 분류한 다음 완료되면 알려줘" 같은 요청)은 타입만
   예약했다(`BrainPlanResult`) — 요청서도 "1차에서 과도하게 개발하지 말 것"을 명시했으므로
   의도적으로 범위 밖에 둠.

## 14. 다음 단계 추천

1. (우선순위 높음) OpenAI 루프를 별도 함수로 뽑아 `FallbackProvider`로 감싸기 — 그러면
   `getOliviaBrain()`이 진짜 자동 선택/폴백 Gateway가 된다. 단, 실제 트래픽이 도는 코드라
   충분한 회귀 테스트와 별도 리뷰 필요.

   `request_quote_publish` 등 기존 APPROVAL_TOOLS와 같은 카드 컴포넌트를 타므로 코드상
   동작은 같지만, 실제 화면에서 "규칙 승인" 문구가 자연스러운지는 안 봤다.

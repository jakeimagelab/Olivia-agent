# Telegram 후속 명령 도구 복원 설계

## 문제

Telegram의 `다시 만들어줘`, `오케이`, `왜 안 돼?` 같은 후속 문장은 현재 메시지만으로 문서 도메인을 알 수 없다. Web은 `recentUserText`를 전달하지만 Telegram은 이를 전달하지 않아 `create_quote` 같은 필수 도구가 후보에서 빠진다. `TOOL_ACTION`으로 분류돼도 모델이 도구를 호출하지 않으면 확인되지 않은 실패 설명이 그대로 저장된다.

## 검토한 접근

1. Telegram 호출부에서 최근 문자열만 전달: 변경은 작지만 다른 채널에서 같은 문제가 반복되고 호출자가 문맥 정확성을 책임져야 한다.
2. 프롬프트만 강화: 모델에게 보이지 않는 도구를 호출하게 할 수 없고 비결정적이다.
3. 서버가 canonical 대화 기록으로 문맥과 실행 상태를 복원: 모든 채널에 동일하게 적용되고 DB 사실 확인까지 강제할 수 있다.

3번을 채택한다. Telegram의 최근 문맥 전달도 빠른 보조 신호로 추가하되, 최종 기준은 stream 서버가 읽은 canonical history다.

## 설계

### 도구 선택

- stream 서버가 저장된 최근 사용자 메시지에서 `recentUserText`를 만든다.
- 호출자가 제공한 문맥과 서버 문맥을 합쳐 도구 도메인을 다시 계산한다.
- `다시`, `그걸로`, `오케이` 같은 후속 표현은 직전 문서 도메인의 도구를 유지한다.

### 실행 보증

- 명확한 `TOOL_ACTION`인데 모델이 첫 라운드에서 도구를 호출하지 않으면 자유 텍스트를 즉시 전달하지 않는다.
- 문맥상 단일 생성 도구가 확정되는 경우 해당 도구를 강제한 재시도를 한 번 수행한다.
- 단일 도구를 확정할 수 없으면 실행하지 않았다는 추측성 설명 대신 필요한 대상을 한 문장으로 확인한다.

### 사실 확인

- `생성되지 않았다`, `저장되지 않았다`는 결론은 문서 조회 도구 결과가 있을 때만 허용한다.
- 후속 실패 질문은 최근 성공 문서 메타데이터와 임시문서 인덱스를 우선 조회한다.
- 도구 미호출을 실제 리소스 부재로 표현하지 않는다.

### 채널 및 엔진 일관성

- Hermes와 cloud fallback은 같은 canonical history와 도구 선택 결과를 사용한다.
- 엔진 전환은 실행 계약을 변경하지 않는다.

## 테스트

- Telegram `견적서 생성` 다음 `다시 만들어줘`에서 `create_quote`가 유지된다.
- 호출자가 `recentUserText`를 누락해도 서버 history로 복원된다.
- `TOOL_ACTION` 첫 응답이 텍스트뿐이면 강제 도구 재시도를 수행한다.
- 실제 문서가 존재할 때 `생성되지 않았다`고 답하지 않는다.
- Hermes 연결 전 실패 후 cloud fallback에서도 같은 도구가 실행된다.

## 완료 기준

- 짧은 Telegram 후속 명령이 직전 문서 도구를 실행한다.
- 실행 기록 없이 성공·실패 사실을 단정하는 응답이 사용자에게 전달되지 않는다.
- 기존 전체 테스트, 타입 검사, 린트와 프로덕션 빌드가 통과한다.

# Olivia 채팅 순서 및 테스트 데이터 정리 설계

작성일: 2026-09-26

## 목표

1. 실시간 동기화 중에도 한 턴의 표시 순서를 `사용자 메시지 → Olivia 진행 상태 → Olivia 최종 답변`으로 보장한다.
2. 운영 DB에 남아 있는 `0922_test_os` 테스트 메타데이터를 정확한 범위로 삭제한다.
3. NAS의 실제 파일은 변경하지 않는다.

## 채팅 순서 원인

웹 요청 직후 로컬 상태에는 사용자 메시지와 스트리밍 중인 Olivia 메시지가 차례대로 추가된다. 이후 Realtime 갱신으로 서버에 저장된 사용자 메시지가 들어오면, 현재 병합 함수는 서버 메시지와 로컬의 스트리밍 메시지를 `createdAt`으로 다시 정렬한다.

서버 사용자 메시지의 저장 시각은 로컬 Olivia 메시지가 만들어진 시각보다 늦을 수 있다. 이 경우 Olivia 진행 메시지가 사용자 메시지보다 먼저 정렬된다.

## 채팅 순서 수정

`mergeConversationMessages()`는 서버 메시지를 기준 목록으로 사용하되, 아직 서버에 저장되지 않은 로컬 진행 메시지의 상대 위치를 보존한다.

- 서버 메시지는 기존처럼 생성 시각 순서로 정렬한다.
- 로컬의 `sending`, `streaming`, `error` 메시지는 중복 여부를 확인한다.
- 로컬 진행 메시지 앞에 있던 사용자 메시지가 서버 메시지로 교체됐으면, 진행 메시지를 그 서버 사용자 메시지 바로 뒤에 삽입한다.
- 연결할 사용자 메시지가 없을 때만 안전한 시간순 폴백을 사용한다.
- 여러 로컬 보류 메시지가 있으면 로컬 배열의 상대 순서를 유지한다.
- 완료된 서버 기록과 Telegram/Web 통합 정렬 정책은 변경하지 않는다.

## 테스트

회귀 테스트에 다음 경우를 추가한다.

1. 로컬 사용자 메시지 뒤에 로컬 스트리밍 Olivia 메시지가 있다.
2. 서버 사용자 메시지의 `createdAt`이 로컬 Olivia 메시지보다 늦다.
3. 병합 후에도 사용자 메시지가 먼저, Olivia 진행 메시지가 바로 다음에 온다.
4. 기존 Web/Telegram 시간순 병합과 optimistic 사용자 메시지 교체 테스트가 계속 통과한다.

## `0922_test_os` 삭제 범위

운영 DB 읽기 전용 점검에서 다음 레코드를 확인했다.

- `photo_storage_projects`: 1건
- `worker_events`: 1건
- `photo_storage_events`: 22건
- `remote_jobs`: 11건
- 연결된 `select_galleries`: 0건
- 연결된 `workflow_runs`: 0건

삭제 순서는 다음과 같다.

1. 프로젝트 ID를 payload로 참조하는 `remote_jobs` 11건 삭제
2. `folder_name = '0922_test_os'`인 `worker_events` 1건 삭제
3. `photo_storage_projects` 1건 삭제
4. 외래키 cascade로 `photo_storage_events` 22건 삭제 확인
5. 동일 이름·프로젝트 ID로 남은 관련 레코드가 0건인지 재조회

`select_galleries`, 고객, 워크플로는 연결된 레코드가 없으므로 변경하지 않는다. NAS 원본·JPG·분류 폴더 등 실제 파일은 삭제하지 않는다.

## 실패 처리

- 삭제 전 대상 ID와 건수를 다시 확인한다.
- 확인된 프로젝트 ID와 정확한 폴더명만 조건으로 사용한다.
- 각 삭제 결과에서 DB 오류를 확인하고, 오류가 있으면 다음 단계를 성공으로 보고하지 않는다.
- 삭제 후 검증에서 하나라도 남아 있으면 완료로 보고하지 않는다.

## 수용 기준

- 새 요청을 보냈을 때 사용자 말풍선이 Olivia 진행 카드 위에 표시된다.
- 스트리밍 및 Realtime 갱신 중에도 순서가 뒤집히지 않는다.
- 기존 대화 병합 테스트가 모두 통과한다.
- `0922_test_os` 관련 운영 DB 테스트 데이터가 0건이다.
- NAS 실제 파일은 변경되지 않는다.

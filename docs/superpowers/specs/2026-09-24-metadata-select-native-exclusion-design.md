# 메타데이터 셀렉 네이티브 창 · 1차 작업본 제외 설계

작성일: 2026-09-24  
대상 리포지토리: `jakeimagelab/Olivia-agent`

## 1. 목표

두 문제를 하나의 작업으로 해결한다.

1. OLIVIA OS에서 메타데이터 셀렉을 열 때 페이지 전체가 iframe으로 들어가 자체 헤더가 중복되는 문제를 없앤다.
2. EXIF 촬영시각으로 찾아낸 원본 JPG를 `JPG전체`에서 형제 폴더 `JPG_보정완료`로 안전하게 옮겨, 2차 셀렉 대상에서 이미 작업한 사진을 제외한다.

기존 EXIF 매칭 알고리즘, RAW 원본 보호 규칙, RAW를 `Selected_RAW`에 복사하는 동작은 유지한다.

## 2. 창 내부 렌더링 구조

### 2.1 메타데이터 셀렉 네이티브 등록

현재 `/metadata-select`는 앱 그리드에는 있지만 `oliviaAppRegistry`에 없어 `legacy-route`와 iframe으로 열린다. 이를 다음 구조로 바꾼다.

- 페이지의 실제 UI와 상태는 재사용 가능한 `MetadataSelectWorkspace` 컴포넌트로 분리한다.
- `app/metadata-select/page.tsx`는 `MetadataSelectWorkspace`를 직접 렌더한다.
- `MetadataSelectWindowContent` 어댑터를 추가하고 `DesktopWindowProvider value={true}` 안에서 같은 워크스페이스를 렌더한다.
- `oliviaAppRegistry`에 `/metadata-select`를 전용 앱으로 등록한다.
- 워크스페이스는 `useDesktopWindowMode()`만 사용해 `GlobalHeader` 표시 여부를 판단한다.

직접 URL에는 데스크톱 창 컨텍스트가 없으므로 헤더가 표시되고, OLIVIA OS 창에서는 헤더가 표시되지 않는다. pathname이나 `oliviaEmbedded` 쿼리로 네이티브 창 여부를 추측하지 않는다.

### 2.2 공통 규칙

새 화면을 OLIVIA OS 창에 붙일 때의 규칙은 다음 하나로 고정한다.

1. 페이지 본문을 재사용 가능한 워크스페이스 컴포넌트로 분리한다.
2. 네이티브 창 어댑터는 `DesktopWindowProvider value={true}`를 제공한다.
3. 워크스페이스는 `useDesktopWindowMode()`로 페이지 전용 크롬(전역 헤더, 바깥 여백 등)을 숨긴다.
4. iframe의 `oliviaEmbedded`는 아직 네이티브 어댑터가 없는 레거시 화면의 호환 신호로만 남긴다.

이 규칙과 현재 어댑터·iframe 화면의 자체 헤더 조사 결과를 별도 감사 문서에 기록한다. 이번 작업에서는 메타데이터 셀렉을 네이티브로 전환하고, 다른 화면은 목록과 실제 증상만 기록한다. 확인 없이 전체 화면을 일괄 전환하지 않는다.

### 2.3 고객관리 확인

고객관리는 이미 `ClientsWindowContent`가 `ClientsWorkspace`를 직접 렌더하는 네이티브 화면이다. 다음 경로를 확인한다.

- 프로젝트 상세, 고객 상세 등 내부 이동이 창 내부 상태 전환을 사용하는지
- 내부 링크가 `/clients?...` 전체 페이지 또는 `legacy-route`로 빠지는지
- 워크스페이스 내부에 전역 헤더와 같은 페이지 크롬이 남아 있는지

문제가 확인되면 기존 네이티브 창 상태 전환을 사용하도록 해당 링크만 수정한다. 고객관리 전체를 다시 만들지 않는다.

## 3. 1차 작업본 제외 UX

### 3.1 옵션과 폴더 선택

`이미 작업한 사진 제외` 옵션은 기본적으로 꺼져 있다.

- 옵션이 꺼짐: 기존과 같이 두 번째 항목에서 `원본 JPG` 폴더를 선택한다.
- 옵션이 켜짐: 두 번째 항목을 `프로젝트 폴더`로 바꾸고 기존 선택값을 초기화한다.
- 프로젝트 폴더 안의 `JPG전체`를 원본 JPG 입력으로 사용한다.
- 같은 프로젝트 폴더에 `JPG_보정완료`를 형제 폴더로 만들거나 기존 폴더를 사용한다.

브라우저 File System Access API는 선택한 하위 폴더에서 부모 폴더로 올라갈 수 없으므로, 옵션을 켰을 때 프로젝트 폴더 권한을 받는 것이 필수다. 폴더 선택 항목 수는 고객 선택본, 프로젝트 폴더, RAW 원본의 세 개로 유지한다.

폴더 이름은 `storageLayout.ts`의 상수로만 선언한다. `JPG전체`, `JPG_보정완료`, `Selected_RAW`를 사용하는 새 코드에 문자열을 중복 작성하지 않는다.

### 3.2 필수 항목과 입력 검증

시작 버튼 근처에 현재 부족한 항목을 구체적으로 표시한다.

- 고객 선택본이 없으면 `고객 선택본을 지정해주세요.`
- 원본 JPG 또는 프로젝트 폴더가 없으면 해당 폴더를 지정하라고 표시한다.
- RAW 원본이 없으면 `RAW 원본을 지정해주세요.`
- 프로젝트 폴더에 `JPG전체`가 없으면 시작하지 않고 정확한 경로를 알린다.

출력 폴더를 입력으로 다시 선택하는 경우도 시작 전에 차단한다.

- RAW 원본으로 `Selected_RAW` 자체 또는 그 하위를 지정할 수 없다.
- 고객 선택본으로 `JPG_보정완료`, `Selected_RAW` 또는 그 하위를 지정할 수 없다.
- 서로 다른 역할의 입력 폴더가 같은 엔트리면 경고한다.

동일 엔트리 확인에는 `isSameEntry()`를 사용하고, 선택한 상위 핸들에서 하위 핸들까지의 관계는 `resolve()`로 확인한다. 브라우저가 관계 확인을 지원하지 않거나 권한이 없으면 실행하지 않고 이유를 표시한다.

## 4. 매칭, 확인, 실행

### 4.1 사전 분석

기존 EXIF `DateTimeOriginal` 매칭 순서는 변경하지 않는다.

1. 원본 JPG 촬영시각 인덱스를 만든다.
2. RAW basename 인덱스를 만든다.
3. 고객 선택본의 EXIF를 읽어 원본 JPG와 RAW를 찾는다.
4. 결과를 화면에 표시하고 파일 변경 없이 대기한다.

`이미 작업한 사진 제외`가 켜져 있으면 다음 조건을 모두 만족해야 실행 확인 단계로 갈 수 있다.

- 모든 선택본이 원본 JPG와 RAW에 성공적으로 매칭됨
- 같은 원본 JPG가 여러 선택본에 중복 매칭되지 않음
- `JPG_보정완료`에 같은 이름의 파일이 없음
- 원본 JPG가 실제 `JPG전체`의 평면 파일임

하나라도 실패하면 RAW 복사와 JPG 이동을 모두 시작하지 않는다. 실패 파일과 원인을 목록으로 보여준다.

### 4.2 명시적 확인

사전 분석이 성공하면 다음 내용을 보여준다.

- 선택본 수
- 복사할 RAW 수
- `JPG전체`에서 제외할 원본 JPG 수
- 대상 폴더 `JPG_보정완료`

사용자가 `N장 제외하고 RAW 복사` 버튼을 눌러야 파일 변경이 시작된다. 취소하면 분석 결과만 남고 파일은 변경되지 않는다.

옵션이 꺼진 기존 RAW 매칭도 분석 결과를 먼저 보여주고 사용자가 확인한 뒤 복사하도록 맞춘다. 파일을 쓰는 작업에는 동일한 확인 원칙을 적용한다.

### 4.3 RAW 복사와 JPG 이동

RAW는 기존처럼 원본을 유지하고 `RAW 원본/Selected_RAW`에 복사한다. RAW 파일을 이동·삭제·이름 변경하지 않는다.

JPG 이동은 다음 순서로 처리한다.

1. 모든 대상과 충돌 여부를 다시 사전 검증한다.
2. 대상 JPG를 `JPG_보정완료`에 복사하고 파일 크기를 확인한다.
3. 전체 복사와 검증이 성공한 뒤에만 `JPG전체`의 원본 JPG를 삭제한다.
4. 복사 중 오류가 나면 이번 실행에서 만든 대상 파일을 지우고 원본은 유지한다.
5. 삭제 중 오류가 나면 이미 삭제한 원본을 검증된 대상 복사본에서 복원하고, 이번 실행의 대상 파일을 정리한다.

브라우저 파일 API에는 트랜잭션이 없으므로 전원 종료 같은 프로세스 밖의 장애까지 원자성을 보장할 수는 없다. 정상적인 API 오류에서는 롤백하고, 롤백 자체가 실패하면 어느 파일이 어느 위치에 남았는지 화면에 구체적으로 표시한다.

## 5. 복구 경로

프로젝트 폴더가 선택돼 있고 `JPG_보정완료`에 JPG가 있으면 `보정완료 사진 복구` 작업을 제공한다.

- 복구 대상은 현재 프로젝트의 `JPG_보정완료`에 있는 모든 JPG다.
- 복구 전 파일 수를 표시하고 확인받는다.
- `JPG전체`에 같은 이름이 하나라도 있으면 아무것도 이동하지 않는다.
- 실행 방식은 정방향과 같은 복사·검증·삭제·롤백 절차를 사용한다.
- 복구가 끝나도 RAW의 `Selected_RAW` 복사본은 건드리지 않는다.

이 방식은 페이지를 새로 열어도 프로젝트 폴더를 다시 지정하면 사용할 수 있으며, 최근 실행에만 의존하지 않는다.

## 6. 상태와 오류 표시

화면 상태는 다음 단계로 분리한다.

- `idle`: 폴더 선택과 필수 항목 안내
- `analyzing`: 원본, RAW, 선택본 분석
- `awaiting_confirmation`: 분석 결과와 실행 확인
- `copying_raw`: RAW 복사
- `moving_jpg`: JPG 제외 처리
- `restoring_jpg`: JPG 복구
- `done`: 결과와 복구 진입점
- `failed`: 실패 단계, 파일명, 롤백 결과 표시

버튼이 비활성화될 때는 반드시 같은 영역에 이유를 표시한다. 진행 중에는 폴더 선택과 옵션 변경을 잠근다.

## 7. 파일과 책임 경계

예상 변경 범위는 다음과 같다.

- `app/metadata-select/page.tsx`: 직접 URL 진입점
- `components/metadata-select/MetadataSelectWorkspace.tsx`: 재사용 UI와 화면 상태
- `components/olivia-os/adapters/MetadataSelectWindowContent.tsx`: 네이티브 창 어댑터
- `components/olivia-os/registry/oliviaAppRegistry.ts`: 앱 등록
- `lib/metadataSelect/`: 폴더 관계 검증, 사전 계획, 안전 이동·복구 헬퍼
- `lib/photo-classifier/node/storageLayout.ts`: `JPG_보정완료` 상수
- `docs/`: 창 내부 헤더 감사 결과와 공통 규칙

EXIF 해석과 매칭의 책임은 기존 `readExifDateTime`과 `matcher`에 남긴다. 안전 이동 헬퍼는 이미 계산된 파일 핸들과 경로만 받아 매칭 판단을 하지 않는다.

## 8. 테스트와 검증

### 8.1 자동 테스트

- `/metadata-select`가 전용 앱으로 해석되는지
- 직접 페이지에서는 헤더가 보이고 네이티브 창에서는 숨겨지는지
- 옵션 전환 시 잘못된 두 번째 폴더 핸들이 초기화되는지
- 필수 폴더별 안내 문구
- 출력 폴더·하위 폴더 입력 차단
- 한 건이라도 매칭 실패하면 실행 계획이 생성되지 않는지
- 목적지 이름 충돌 시 아무 파일도 바뀌지 않는지
- 복사 실패와 삭제 실패 시 롤백하는지
- `JPG_보정완료` 전체 복구와 복구 충돌 중단
- 기존 EXIF 매칭 테스트와 RAW 보호 테스트 유지

### 8.2 전체 검증

1. `npm run typecheck`
2. `npm test`
3. `npm run build`
4. 직접 `/metadata-select` 진입과 OLIVIA OS 창 진입 비교
5. 테스트 폴더로 성공, 매칭 실패, 이름 충돌, 복구 흐름 확인

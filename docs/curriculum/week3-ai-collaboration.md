## 슬라이드 2. 실제 예시 — 진짜 지시서는 이렇게 생겼다

아래는 실제로 사용된 지시서 원문 일부입니다 ("오늘의 마지막 수정" 인수인계 문서에서 발췌).

```
오늘의 마지막 수정

1. 올리비아채팅창 전체화면, 중간화면, 작은 화면(현재 사이즈) 버튼 넣어줘
2. 어드민 홈 화면 재구성
   - 대상: app/admin/dashboard/home/page.tsx, components/admin/AdminSidebar.tsx
   - 목적: 홈 화면에 동급으로 나열된 구역이 너무 많아 복잡해 보이는 문제를 해결.
     브리핑카드·일정카드·명언위젯은 그대로 유지.
...
```

**이 지시서가 좋은 이유**
- "무엇을"뿐 아니라 "왜"(목적)가 있음 → AI가 판단이 필요한 순간에 방향을 잃지 않음
- "그대로 유지"할 것을 명시 → 안 건드려도 되는 부분까지 AI가 건드리는 걸 방지
- 화면 이름/기능 이름을 구체적으로 지칭 → "그거", "저거" 대신 정확한 대상

**비개발자도 이렇게 쓸 수 있는 이유**: 파일 경로(`app/...`)는 몰라도 됩니다. "무엇을, 왜, 무엇은 그대로 두고"만 정확히 말하면 AI가 나머지를 채웁니다.

## 슬라이드 3. 나쁜 지시 vs 좋은 지시

| 나쁜 지시 | 좋은 지시 |
|---|---|
| "홈 화면 좀 정리해줘" | "홈 화면에 구역이 너무 많아 복잡해 보여. 브리핑카드·일정카드·명언위젯은 그대로 두고, 나머지를 하나로 묶어줘" |
| "버튼 추가해줘" | "올리비아 채팅창에 전체화면/중간화면/작은화면(현재 사이즈), 이렇게 3가지 크기를 고를 수 있는 버튼을 추가해줘" |
| "안 돼요" | "고객 목록에서 방금 승인 완료한 A병원이 '완료'가 아니라 '미시작'으로 나와요" |

**공통 규칙**: 목표(무엇이 되어야 하는가) + 현재 상태(지금 뭐가 문제인가) + 유지할 것(건드리면 안 되는 것)

## 슬라이드 4. 실제 예시 — 올리비아의 12단계 워크플로우

올리비아가 실제로 관리하는 촬영 프로젝트의 12단계입니다.

```
1. 상담 / 미팅
2. 견적서 생성 / 전달        ← 승인 필요, 고객에게 노출됨
3. 계약서 작성 / 전달        ← 승인 필요, 고객에게 노출됨
4. 콘티 작성 / 전달          ← 고객에게 노출됨
5. 촬영
6. 결제 확인
7. 백업 정리
8. 고객 선택 (셀렉 갤러리)
9. 리터칭
10. 최종 납품
11. 수정
12. 리워드
```

각 단계는 데이터베이스 안에서 아래 정보를 함께 갖고 있습니다.
- 이 단계는 **승인이 필요한가?** (`requires_approval`)
- 이 단계는 **자동으로 메일 초안을 만드는가?** (`creates_mailing_draft`)
- 이 단계는 **고객에게 보여도 되는가?** (`visible_to_client`)

**핵심 문장**: 업무를 자동화한다는 건 이렇게 **"단계 하나하나에 이름을 붙이고, 각 단계의 규칙을 정하는 것"**입니다. 코드가 아니라 기획입니다.

## 슬라이드 5. 실제 화면 — 승인 대기함

![승인 대기함](../../cmp-3-approvals.png)

- "운정표병원 최종파일 전달 승인" — 최종 보정본을 병원에 보내기 전, 사람이 마지막으로 확인
- "브라보마취통증의학과 견적서 초안 승인" — 금액(2,000,000원)과 패키지 구성을 확인 후 승인
- 각 카드에는 **승인하고 고객에게 공개 / 수정 요청 / 반려** 3가지 선택지

**왜 승인 단계를 넣는가**: 자동화해도 "고객에게 실제로 나가는 순간"처럼 되돌리기 어려운 지점에는 반드시 사람 확인을 넣습니다. 견적서 2번, 계약서 3번 단계가 그래서 `requires_approval = true`입니다.

## 슬라이드 6. 데이터 구조 기초 — 테이블은 엑셀 시트다

| workflow_runs (진행 중인 프로젝트) 테이블 예시 | |
|---|---|
| client_name | 운정표병원 |
| project_name | 브랜드 촬영 4월 |
| current_step_key | conti (콘티 작성/전달) |
| status | active |

한 줄(row) = 프로젝트 하나, 각 칸(column) = 그 프로젝트의 속성 하나. "데이터베이스 설계"는 결국 **"우리 업무에서 뭘 기록해야 하는지 항목을 정하는 것"**과 같습니다.

## 슬라이드 7. 실제 버그 사례 1 — 진행률이 어긋난 사고

실제 코드에 남아있는 주석입니다 (버그를 고치면서 원인을 기록해둔 것).

> "WORKFLOW_STEPS(전체 18단계 카탈로그)의 마지막 원소는 배열 선언 순서상 우연히 `payment_confirm`이라, 진행률 표시(활성 12단계 기준 계산)와 어긋나는 버그가 있었다."

**쉽게 설명하면**: 시스템 내부에는 "전체 18단계짜리 큰 목록"과 "실제로 화면에 쓰는 12단계 목록" 두 개가 있었는데, 어떤 계산은 18단계 기준으로, 어떤 계산은 12단계 기준으로 하고 있어서 "6/12"처럼 숫자가 서로 안 맞았습니다.

**여기서 배우는 것**: 같은 것을 가리키는 "기준"이 시스템 안에 두 개 이상 있으면 반드시 어긋나는 순간이 옵니다. 비개발자가 이 버그를 발견했다면 이렇게 설명하면 충분합니다 → *"프로젝트 상세 화면에서는 6/12라고 나오는데, 목록 화면 진행률은 다르게 계산되는 것 같아요"*. 원인(배열 순서)은 AI가 코드를 보고 찾아냅니다. **사람은 "어디서, 무엇이 다르게 보이는지"만 정확히 짚으면 됩니다.**

## 슬라이드 8. 실제 버그 사례 2 — "미시작"으로 잘못 표시되던 사고

- 고객 목록 화면은 원래 **진행 중(active)인 프로젝트만** 가져오도록 되어 있었습니다
- 그런데 올리비아가 프로젝트를 "전체완료"로 처리하면 상태가 `completed`로 바뀌는데, 목록 화면은 여전히 `active`만 찾고 있어서 **완료된 프로젝트가 목록에서 사라져 "미시작"처럼 보이는** 문제가 생겼습니다
- 고침: `completed` 상태도 함께 가져오도록 수정하고, 완료 건은 초록색 "완료" 배지로 표시

**같은 교훈**: "화면에 뭐가 보이는가"와 "실제 데이터가 어떤 상태인가"가 다를 때, 원인은 대부분 "화면이 데이터를 가져올 때 빠뜨린 조건"에 있습니다.

# Olivia 작업실 UI 통일

Olivia의 새 기능이 기존 제품과 같은 시각 언어와 동작 설명을 사용하도록 한다. 사진·영상 작업실에는 전체 규칙을 적용하고, 작업실 밖의 새 기능에는 기존 화면 구조와 충돌하지 않는 공통 표현 원칙만 적용한다.

## 작업 전에 반드시 읽을 기준

저장소 루트의 다음 자료를 작업 전에 확인한다.

1. [`UI(Skill)/작업실_UI통일_요청서.md`](../../../UI(Skill)/작업실_UI통일_요청서.md)를 끝까지 읽는다.
2. UI를 만들거나 바꾸는 작업이면 아래 여섯 이미지를 모두 직접 확인한다.
   - [`01 · 색@2x.png`](../../../UI(Skill)/01%20%C2%B7%20색@2x.png)
   - [`02 · 탭@2x.png`](../../../UI(Skill)/02%20%C2%B7%20탭@2x.png)
   - [`03 · 버튼@2x.png`](../../../UI(Skill)/03%20%C2%B7%20버튼@2x.png)
   - [`04 · 목록과 글@2x.png`](../../../UI(Skill)/04%20%C2%B7%20목록과%20글@2x.png)
   - [`05 · 최종 화면@2x.png`](../../../UI(Skill)/05%20%C2%B7%20최종%20화면@2x.png)
   - [`06 · 기능에서 나온 것@2x.png`](../../../UI(Skill)/06%20%C2%B7%20기능에서%20나온%20것@2x.png)
3. 대상 화면의 기존 컴포넌트, 데이터 흐름, API 호출, 공통 부품을 먼저 확인한다. 위치와 겉모습을 바꾸는 요청으로 기능 로직을 바꾸지 않는다.

현재 사용자의 구체적인 요구가 가장 우선한다. 그다음은 요청서의 글, 그다음은 이미지의 시각 예시 순으로 판단한다. 요청서에 값이 없는 속성은 추측해서 바꾸지 않는다.

원문 요청서의 파일 경로, 줄 번호, 특정 컴포넌트 수정, `파일을 새로 만들지 않는다`, 19곳 개수, 8장 완료표는 2026-10-05 사진작업실 정리 작업에만 해당한다. 새 기능에 그대로 반복하지 않는다. 새 기능에서는 아래의 제품 규칙과 현재 요청의 범위를 적용하고, 원문의 구체적인 기존 파일 수정은 그 파일을 실제로 고치는 요청일 때만 수행한다.

## 제품 규칙

### 1. 화면 목적에 따라 톤을 정한다

- 사진이나 영상의 색을 실제로 판단하는 작업 영역은 `#2A2A2A` 중성 다크다. 그라데이션을 넣지 않는다.
- 목록, 기획, 글쓰기, 폼, 사용 가이드는 밝은 바탕 `#FDFCFA`와 흰 카드다.
- 같은 기능은 로컬/원격 실행 위치가 달라도 같은 톤을 유지한다.
- 밝은 화면의 주조는 `#155855`, 주 실행은 `#C94A1E`, 흐린 글자는 `#5A7470`이다.
- 어두운 패널의 주 실행은 `#37C39D`와 글자 `#103E36`, 선택 표시는 `#4FD8B8`이다. 속 카드는 `rgba(255,255,255,.04)`, 테두리는 `rgba(255,255,255,.10)`을 쓴다.
- 파란 강조색, 작업실 전용 임의 색, 로컬 색 상수 묶음을 새로 만들지 않는다. 기존 공통 토큰과 공통 부품을 먼저 쓴다.

### 2. 탭은 두 단계만 쓴다

- 1단계 작업실 탭은 회색 알약 바 안의 흰 알약 선택 상태다. 선택된 탭만 `#155855` 글자와 선 아이콘을 쓴다.
- 2단계 패널 서브탭은 밑줄형이다. 어두운 패널에서는 선택된 탭에 흰 글자와 `#4FD8B8` 2px 밑줄을 쓴다.
- 세 번째 탭 모양을 만들지 않는다.
- 탭 아이콘은 `lucide-react` 선 아이콘을 사용한다. 이모지, 컬러 네모 아이콘, 탭별 임의 장식은 쓰지 않는다.

### 3. 버튼 역할을 먼저 정한다

- 역할은 주 실행, 보조, 약함, 비활성 네 가지다.
- 채운 주 실행 버튼은 한 화면에 하나다. 밝은 화면에서는 주황, 어두운 패널에서는 민트를 쓴다.
- 보조 버튼은 밝은 화면에서 초록 외곽선, 어두운 패널에서 흰색 저채도 외곽선이다.
- 약한 동작은 배경과 테두리 없이 흐린 글자로 표시한다.
- 비활성 버튼은 투명 배경과 약한 외곽선만 사용한다. 원래 버튼 색에 `opacity`만 낮추지 않는다.
- 같은 동작은 같은 이름과 같은 위치를 유지한다. 화살표는 탭이나 단계 이동에만 쓴다.
- 포함 관계가 있는 두 동작은 이름만 보고 차이를 알 수 있게 한다. 예: `선택만 저장`과 `저장하고 RAW 매칭으로`.

### 4. 목록과 글을 읽는 순서대로 만든다

- 동일 종류의 항목 목록은 카드 그리드보다 가로 리스트 행을 우선한다. 이미지 후보처럼 시각 비교가 목적인 콘텐츠는 예외다.
- 시간은 상대 표기로 보여주고, 정확한 시각은 툴팁이나 상세에서 제공한다.
- 단계 번호는 한 자리 원형으로 통일한다. `01`, `02` 형식을 만들지 않는다.
- 글자 굵기는 600을 넘기지 않는다. 본문 400, 제목 500~600, 강조 500을 기준으로 한다.
- 본문에서 카드와 장식이 정보를 압도하지 않게 한다.

### 5. 화면, 가이드, 코드의 순서를 맞춘다

- 사용 가이드는 밝은 패널로 유지하고 보통 3~4단계로 구성한다.
- 실제 화면의 입력 순서, 가이드 단계, 코드의 필수조건 순서를 같게 한다.
- 비활성 동작에는 사용자가 다음에 해야 할 일을 한 줄로 알린다. 예: `폴더를 먼저 선택하세요.`
- 사용할 수 없는 기능은 누른 뒤에만 알리지 말고 탭에서 미리 흐림, 자물쇠, 툴팁 등으로 표시한다. 기존 안내 동작은 보존한다.
- 진행 상태는 한 곳에 모아 보여준다. 실제로 일시정지를 지원할 때만 일시정지 조작을 제공한다.
- 점수, 배지, 개수는 기준과 의미를 이름에 드러낸다. 설명할 수 없는 수치는 노출하지 않는다.

### 6. 기능을 보존한다

- 사용자가 기능 변경을 요청하지 않았다면 데이터 구조, API, 저장 방식, 분석 로직, 파일 처리, 권한, 공유 링크를 바꾸지 않는다.
- 기존 공통 작업실 셸, 탭, 실행 위치 바, 가이드, 스테퍼, 토스트, 확인창을 우선 재사용한다.
- 로컬과 원격의 지원 범위가 다르면 차이를 숨기지 않되, 동일 기능의 시각 톤과 정보 구조는 유지한다.
- 현재 요청에 적히지 않은 개선을 함께 넣지 않는다.

## 구현 순서

1. 화면을 `보는 화면`과 `쓰는 화면` 중 하나로 분류한다.
2. 기존 공통 부품과 가장 가까운 작업실 화면을 찾아 재사용 범위를 정한다.
3. 1단계 탭, 2단계 서브탭, 작업 패널, 가이드의 정보 구조를 먼저 맞춘다.
4. 주 실행 하나와 나머지 버튼 역할을 지정한다.
5. 빈 상태, 비활성 이유, 진행, 실패 상태가 조용히 사라지지 않는지 확인한다.
6. 기능 로직을 보존한 최소 변경으로 구현한다.

## 완료 전 확인

- 새 색, 세 번째 탭 스타일, 이모지 탭, 채운 CTA 두 개가 생기지 않았는가?
- 사진·영상 판단 패널이 중성 다크이고, 글쓰기·가이드 패널이 밝은가?
- 로컬/원격 전환으로 같은 기능의 패널 톤이 뒤집히지 않는가?
- 화면 순서와 가이드 순서가 같은가?
- 비활성 또는 사용할 수 없는 이유가 사용자에게 보이는가?
- 기능, 데이터, API와 외부 공유 경로가 요청 없이 바뀌지 않았는가?
- 넓은 폭과 좁은 폭에서 실제 화면을 확인했는가?
- 관련 타입 검사, 린트, 테스트를 실행하고 미실시 항목을 명시했는가?

최종 보고에는 적용한 톤, 탭 단계 수, 주 실행 버튼, 재사용한 공통 부품, 보존한 기능, 실행한 검증과 미실시 검증을 적는다.
